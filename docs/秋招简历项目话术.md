## 二、面试自我陈述话术（30 秒电梯演讲）

> 我独立做了一个叫 MokioClaw 的 AI Coding Agent，对标的是 Anthropic 的 Claude Code。它不是套壳调 API，而是从引擎层开始逆向实现：用 LangGraph 搭多智能体工作流，自研了工具执行管线、五级上下文压缩、token 预算恢复链、MCP 协议接入和安全沙箱。整个项目两万多行代码、三百多个测试。我做这个项目的目的是搞清楚一个生产级 Agent 的「运行壳（harness）」到底要处理哪些工程问题——比如工具输出爆了怎么落盘、上下文超长怎么压缩、子 Agent 做了危险操作怎么拦截——这些是纯调 API 学不到的。

## 三、核心亮点深挖准备（每个都是面试官的高频追问点）

下面每个亮点都按「**是什么 → 为什么这么做 → 代码在哪 → 可能被追问的点**」组织，确保能接住深挖。

### 亮点 1：引擎层恢复链（最容易出彩，面试官最爱问「健壮性」）

**是什么**：对齐 Claude Code，处理 LLM 调用的三种异常情况：
1. **token 预算追踪**：`BudgetTracker` 累计输出 token，达 90% 预算或「连续两次增量都小于阈值（收益递减）」时主动停止，注入 nudge 消息。
2. **max_output_tokens 截断恢复**：检测 `finish_reason=length`（模型被截断），两阶段恢复——先 escalate（把 `max_tokens` 从 8k 升到 64k 重试），再用尽则注入 resume 消息让模型继续。
3. **prompt-too-long 恢复**：捕获 413/上下文超长异常，触发 `force_compact`（应急压缩：保留 system + 最近 10 条，中间折叠为摘要），重试一次。

**为什么这么做**：纯调 API 时，模型截断 / 上下文超长会直接抛异常让整个任务失败。生产级 Agent 必须能自愈——这是「harness engineering」的核心。

**代码在哪**：`src/mokioclaw/reliability/token_budget.py`（276 行）+ `orchestration/agent_loop.py`

**会被深挖的点 + 你的回答**：

- **Q：收益递减为什么要「连续两次」小增量才触发？**
  A：单次小增量可能只是模型在等工具结果或思考，不代表真的收益递减。Claude Code 的设计是看趋势——连续两轮都没进展才停。我一开始实现错了，先覆盖 `last_delta_tokens` 再比较，等价于只看一次，被 code review 发现后修成了先比较后覆盖。（这体现你对状态机时序的理解）

- **Q：escalate 后重试同一轮，token 怎么处理？**
  A：escalate 时 `messages.pop()` 撤回那条被截断的 response，但 `budget.account()` 已经把它的 token 计入基线了。如果不回滚，重试后会重复计数污染预算。所以我在 pop 前先 `accounted_tokens = budget.account(response)`，pop 时 `budget.total_output_tokens -= accounted_tokens`，同时 `loops_done -= 1` 让这一轮不消耗循环次数。

- **Q：`max_tokens` 和 `max_completion_tokens` 为什么传两个？**
  A：LangChain 的 ChatOpenAI 有个 alias——`max_tokens` 字段实际别名叫 `max_completion_tokens`，运行时会重命名。但某些推理模型只认 `max_completion_tokens`。`.bind(max_tokens=)` 在这些模型上可能不生效，所以两个都传，双键覆盖保底。

- **Q：模型降级怎么做的？**
  A：`invoke_with_fallback` 支持配置 `MODEL_FALLBACKS`（逗号分隔），主模型失败按列表降级。但 `BadRequestError`（400，比如上下文超长）不降级——因为换模型也救不了，应该走 prompt-too-long 恢复。我用类名判定 `_is_bad_request`，避免硬依赖 openai 包（教学项目不强耦合第三方）。全部失败抛 `FallbackTriggeredError`。

### 亮点 2：MCP 协议接入（体现你懂协议设计 + 并发）

**是什么**：实现了 MCP（Model Context Protocol）客户端，支持两种传输：stdio（子进程）和 HTTP/SSE（远程）。支持 `tools/list`、`resources/list`、`resources/read`，握手时自动探测 server capabilities 预取资源。

**为什么这么做**：MCP 是 Anthropic 推的让 Agent 接外部工具/数据源的标准协议。支持它意味着 Agent 能接任意 MCP server（数据库、文件系统、第三方 API）。

**代码在哪**：`src/mokioclaw/mcp/`（transport.py / client.py / bridge.py / disclosure.py）

**会被深挖的点 + 你的回答**：

- **Q：HTTP/SSE 传输为什么用 urllib 不用 httpx？**
  A：教学项目要零额外依赖、可读性强。urllib 是 stdlib，够了。SSE 流我用后台线程逐行读，按空行聚合多行 `data:` 事件（SSE 规范：一个事件可含多行 data，空行分隔）。

- **Q：SSE 流的并发问题你怎么处理的？**（这是真实踩过的坑）
  A：有三个坑，都是 code review 发现的：
  1. **赋值竞态**：`send()` 处理 SSE 响应时，先 `_close_sse_stream()`（锁内清空）再锁外赋值 `_sse_response = resp`，多线程并发 send 会竞态。修法：把「关闭旧流 + 赋值新流 + start 线程」收敛到单一临界区 `_start_sse_stream()`。
  2. **EOF 后传输失效**：`_read_sse_stream` 的 finally 原来无条件 `_connected=False`，SSE 流自然结束后传输永久不可用。修法：finally 里判断「如果 `_sse_response` 仍指向本线程的 resp」才清空 + close，不再置 `_connected=False`（SSE 流结束 ≠ HTTP 端点不可达）。
  3. **socket 泄漏**：流结束后不 close resp，socket 泄漏到 GC。修法同上，finally 里 `resp.close()`。

- **Q：bridge 的锁怎么设计的？**
  A：原来 `list_tools`/`list_resources` 在 `self._lock` 内直接调 client 做 JSON-RPC（最坏 60s 超时），持锁期间所有 bridge 操作卡死。修法：锁内只取 client 快照，阻塞 I/O 移到锁外（和 `_rebuild_tools` 已有的模式对齐）。

- **Q：resources 怎么避免每次都拉取？**
  A：`list_resources` 用 `_resources_fetched` 布尔标志区分「没拉过」和「拉到了但空」（原来用空列表 falsy 判断，无资源 server 每次都重拉）。握手时若 server capabilities 含 resources 就预取，超时用 5s 而非默认 60s，避免拖慢 connect。

### 亮点 3：五级上下文压缩（体现 Context Engineering）

**是什么**：当对话变长时，分五级处理上下文，从 0 成本规则压缩到 LLM 语义压缩：

| 级别 | 机制 | 成本 |
|------|------|------|
| L1 | 工具结果预算（`ToolResultBudget`）：大输出落盘，messages 只留预览 + 路径 | 0（规则） |
| L2 | `microcompact`：过期 FileRead 结果替换为摘要、超大字段截断 | 0（规则） |
| L3 | `snip`：消息级规则裁剪 | 0（规则） |
| L4 | `force_compact`：应急压缩，保留 system + 最近 N 条，中间折叠 | 0（规则） |
| L5 | `context_compressor_node`：LLM 语义压缩历史消息 | 高（LLM） |

**为什么这么做**：上下文不是越长越好，要放在正确位置。规则压缩能解决 80% 问题且零成本，只有规则搞不定才请 LLM。

**代码在哪**：`src/mokioclaw/memory/`（microcompact.py / snip.py / tool_result_budget.py）+ `orchestration/nodes.py`

**会被深挖的点 + 你的回答**：

- **Q：工具结果落盘的预览怎么生成？**
  A：`ToolResultBudget._truncate_value` 递归截断 str/list/dict。这里踩过坑——原来只截断 str 和 list，dict 值走 else 原样拷贝，嵌套大字典（`{"data": {"big": "x"*60000}}`）经 json.dumps 直接进上下文，预算失效。修法：dict 也序列化测量超阈值就摘要。

- **Q：落盘文件名怎么避免碰撞？**
  A：原来用秒级时间戳 `_%Y%m%d_%H%M%S`，同一秒两个并行只读工具落盘会覆盖。修法：加进程内单调计数器 `_seq`。

- **Q：force_compact 保留 system 时会重复吗？**
  A：会。原来 head 扫全表收 system、tail 固定取末尾，若 system 在 tail 范围内会重复。修法：收集 head 时跳过已落入 tail 的消息（用 `id()` 判等）。

### 亮点 4：安全沙箱 + 两段式分类器（体现安全工程）

**是什么**：
1. **沙箱**：`sandbox.py` 做路径边界检查（防越界写盘）、可选剥离代理变量（网络约束）、危险命令正则拦截。
2. **分类器**：`classifier.py` 两段式——fast-path 规则（只读命令白名单直接放行、毁灭性命令直接拒绝）→ LLM 评估（规则未覆盖时用轻量模型按上下文判 allow/deny/ask）。
3. **handoff 审查**：`classify_handoff` 在子 Agent 结果交回父级前审查其行为摘要，防子 Agent 在委派期间做危险操作。
4. **agent_mode 门禁**：5 种模式（auto/plan/approve/edit/bypass）控制工具放行。

**为什么这么做**：安全是设计的起点不是补丁。规则 fast-path 能秒判已知安全/危险，只有灰区才请 LLM（省 token + 快）。Claude Code 的 `yoloClassifier` 就是这个思路。

**代码在哪**：`src/mokioclaw/security/`（classifier.py / sandbox.py / agent_mode.py / approval.py）+ `tools/agent_tool.py`

**会被深挖的点 + 你的回答**：

- **Q：分类器的 prompt 模板有坑吗？**
  A：有。prompt 里写了 JSON 示例 `{"decision":...}`，用 `.format()` 渲染时 `{` 会被当成占位符抛 `KeyError: '"decision"'`，导致 LLM 分类器**从未被调用**（静默失效）。修法：`{`→`{{` 转义。这个 bug 让我深刻理解了「静默失败是最危险的」。

- **Q：handoff 的 hard-deny 正则怎么避免误伤？**
  A：原来 `rm -rf` 无脑 DENY，连 `rm -rf node_modules`（工作区清理）都拦。修法：细化正则只匹配系统路径（`/`、`~`、`/home` 等），工作区内清理放行。

- **Q：JSON 解析的正则有 ReDoS / 误匹配吗？**
  A：有。`_extract_json` 原来用 `\{[^{}]*\}` 只匹配最内层不含花括号的块，当 LLM 的 reason 字段含 `{path}` 时会误匹配到内层片段导致解析失败。修法：重写为平衡花括号扫描器，处理字符串转义，找第一个能 `json.loads` 成功的对象。

- **Q：路径遍历怎么防的？**
  A：`TopicStore` 的 `read_topic`/`write_topic` 原来直接拼 `name`，传 `../../../etc/passwd` 能越界。修法：`_safe_topic_name` 白名单字符校验（只允许字母数字下划线连字符中文），拒绝 `..`/`/`/`\`。

- **Q：Windows 路径边界检查的坑？**
  A：原来用 `str(resolved).startswith(str(workspace))`，`workspace=D:/a/b` 会误放行 `D:/a/b-c`（前缀匹配无边界）。修法：用 `Path.is_relative_to()` 做真正的路径关系判断。

### 亮点 5：Hook 系统 + 后台任务（体现可扩展性）

**是什么**：
1. **Hook 系统**：7 类事件（PreToolUse/PostToolUse/PostToolUseFailure/Stop/SessionStart/SessionEnd/PreCompact），3 种 handler 类型（command 执行外部命令 / http POST / prompt LLM 评审）。
2. **后台任务**：守护线程执行记忆提取（AutoMemory）和记忆整理（AutoDream），不阻塞主循环。
3. **Agent 工具**：`fork_subagent` 支持子 Agent 嵌套（深度限制），结果经 handoff 分类器审查。

**为什么这么做**：Hook 让用户不改源码就能注入策略（比如 PreToolUse 拦截某些命令、PostToolUse 发通知）。对齐 Claude Code 的 hooks.json。

**代码在哪**：`src/mokioclaw/core/`（hooks.py / hook_loader.py）+ `reliability/background_tasks.py` + `tools/agent_tool.py`

**会被深挖的点 + 你的回答**：

- **Q：http hook 的 4xx/5xx 怎么区分？**
  A：这里踩过大坑。`urllib` 的 `urlopen` 对 4xx 和 5xx **都抛 HTTPError**（HTTPError 是 URLError 子类）。原来第一个 except 捕获所有 HTTPError 无条件 `blocked=True`，导致 5xx（服务端错误）也阻断工具执行，与「5xx 告警不阻断」的契约矛盾。修法：except 内按 `exc.code` 区分，4xx 阻断、5xx 告警放行。

- **Q：记忆层并发写怎么处理？**
  A：AutoMemory 的 `trigger_background_extraction`（守护线程写 MEMORY.md）和主线程的 `maybe_write_explicit_memory`（同步写）会并发 read-modify-write 同一文件，GIL 保护不了三次独立调用（read_text→拼接→write_text），后写者覆盖前写者导致 lost-update。修法：`TopicStore` 加 `_write_lock`，`_update_index` 改 tmp + `os.replace` 原子写；AutoDream 和 session counter 用模块级 `_dream_meta_lock`。另外循环内 `existing` 快照不刷新会导致去重失效，修法是每次 write 后重新 `load_index()`。

### 亮点 6：生产级 RAG 模块（体现检索系统设计 + 抽象能力）

**是什么**：项目内嵌一个面向 Web 端（FastAPI）的完整 RAG 系统，覆盖基础 RAG → 高级 RAG → 工程化的全部能力。不是 demo，是生产标准：

1. **父子分块（Parent-Child Chunk）**：parent 块保完整上下文不向量化，child 块细粒度切片供向量检索，child 绑定 parent_id。查询命中 child → 取回 parent 原文，解决「分块太短缺上下文、太长噪声大」。
2. **结构感知分割**：splitter 按 Markdown 标题层级切分（保留 heading_path 元数据）、代码围栏保护（不腰斩）、递归字符降级 + overlap。对齐 RAG 演进——朴素固定字符切分会割裂语义。
3. **混合检索 + RRF 融合**：向量召回（语义）+ BM25 召回（专有名词/编号/数字强召回）→ RRF（Reciprocal Rank Fusion）去重融合。解决「向量语义强但专有名词召回弱」。
4. **版本控制 + 逻辑删除**：文档更新 version+1，旧版本标记 `deleted=True`，查询自动过滤。不做局部增量更新（易 chunk 偏移），逻辑删除保留可审计性。
5. **可降级 reranker**：onnxruntime 跑 cross-encoder 精排过滤脏数据，模型未配置/推理失败自动降级到 RRF 结果 + 记 trace 降级标记。
6. **全链路 trace_id**：每请求唯一 trace_id 贯穿 retrieve/rerank 各步，记录召回数/分数/耗时/降级，落 jsonl。生产可排查、DEBUG 可查完整链路。
7. **存储抽象**：`StoreBackend` Protocol 定义 6 个方法，默认 `LocalFileBackend`（ChromaDB child 向量 + JSON parent 原文），将来换 Postgres/ES 只实现这 6 个方法，业务零改。
8. **Query 改写**：Multi-Query（一个问句扩成多角度问句多路检索）/ HyDE（生成假设性答案缩小 query-doc 语义鸿沟）/ Step-Back（具体问题抽象成上位概念）三策略，LLM 不可用全部降级为原 query。
9. **Lost-in-the-Middle 重排**：按相关度把最相关片段放头尾、弱相关放中间，规避 LLM 对长上下文中间信息利用率低的 LIM 效应（Liu et al. 2023）。纯规则零成本。
10. **语义缓存**：`CacheBackend` Protocol（默认 `LocalFileCache` JSON 本地实现，可换 Redis）。精确命中 + 语义命中（余弦相似度超阈值），TTL 失效，相同/相近 query 直接返回缓存省 LLM 调用。
11. **引用溯源**：答案里标注 `[n]` 引用对应上下文片段编号，校验引用合法性（防 LLM 编造引用），输出带 doc_id + source 的来源列表。支持 `[1]` `[1,2]` `[1-3]` 多格式。
12. **答案生成 + 强制约束**：LLM 基于上下文生成带引用答案，prompt 强制约束「仅基于上下文、禁幻觉、无答案时拒答」，LLM 不可用降级直出片段。
13. **Self-Query**：LLM 从自然语言问题提取结构化过滤条件（type/version/source），字段白名单防注入，只做确定性字段，复杂时间/否定降级空 filter。
14. **Guardrails 输出护栏**：答案输出前过护栏，拦截敏感信息泄漏（API key/token/手机号/邮箱/身份证）+ prompt injection 越界话题（如「ignore previous instructions」），命中替换为拒答话术 + 记 trace 降级。

**为什么这么做**：基础 RAG 的 8 大缺陷（专有名词召回弱、上下文残缺、脏数据、无法过滤、更新不一致、模糊问题、无法溯源、无监控）要逐个解决，但不能堆砌成 GraphRAG/Agent 那种复杂度。原则是「中小公司完全够用、线上稳定、可排查、可迭代」——算法层做对（父子分块/混合检索/rerank），工程层做实（版本/溯源/可观测/降级），砍掉没真实流量验证的分支（ES 双模式/Milvus）。

**代码在哪**：`src/mokioclaw/rag/`（backend.py 存储抽象 / backends/local_file.py 默认实现 / retrieval.py 混合检索 / reranker.py / trace.py / query_transform.py / reorder.py / context_builder.py / cache.py / citation.py / answer.py / self_query.py / guardrails.py / splitter.py / service.py）

**会被深挖的点 + 你的回答**：

- **Q：为什么父子分块要分两层存储？**
  A：父块和子块的访问模式不同——子块要被向量检索（高频、需向量化、细粒度），父块只在子块命中后取回（低频、不需向量化、保完整上下文）。分两层让向量库只存子块向量（省空间、检索快），父块原文存 JSON 按需取。查询时 child 命中 → parent_id 取父块，保证返回的上下文是完整的段落而非被腰斩的片段。

- **Q：BM25 为什么不引 jieba 做中文分词？**
  A：减法原则。中文分词的友好性靠 child 切分时的结构感知保证——splitter 按标题/段落边界切，child 本身就是语义完整的小片段，`str.split()` 在这个粒度上够用。引 jieba 增加依赖、增加分词歧义处理成本，对中小知识库体量收益不抵复杂度。真到需要细粒度分词的体量，那也该上 ES 了。

- **Q：RRF 为什么用 1/(k+rank) 这个公式？k=60 怎么来的？**
  A：RRF 的核心是「不看绝对分数只看排名」，解决向量分数和 BM25 分数量纲不一致无法直接相加的问题。k 是平滑常数——k 越大，头部和尾部排名的权重差越小，融合越平滑；k 越小越偏向头部。60 是 RRF 原论文的经验值，工业界常用。两路都命中的 chunk 分数叠加自然排前，这就是「混合检索优于单路」的机制。

- **Q：版本控制为什么用逻辑删除不直接物理删？**
  A：两个原因：一是可审计性——文档更新出问题时能回溯旧版本；二是增量安全——物理删 Chroma 记录要按 doc_id where 过滤批量删，操作中出错会留脏数据。逻辑删除只改 metadata 的 `deleted=True`，查询 filter 自动排除，是幂等且可回滚的。重新入库新版本时，旧版本 metadata 统一标记 deleted，查询只取 max version 且未删除的。

- **Q：reranker 的降级链路真的验证过吗？**
  A：验证过。`Reranker.available` 在模型未配置时返回 False，`rerank` 直接返回输入原序（即 RRF 结果）。测试 `test_reranker_degrades_when_no_model` 覆盖了这个路径。但我要诚实说——真实 bge-reranker onnx 模型的输入适配（tokenize、输入张量构造）目前是占位实现（token overlap），需要拿到具体模型文件后补。框架和降级链路是真的，生产模型按需加载。这比假装跑过完整 cross-encoder 更经得住深挖。

- **Q：存储抽象为什么用 Protocol 不用 ABC？**
  A：Protocol 是结构性子类型（鸭子类型），实现方不需要继承，符合项目里 `Embedder` Protocol 的既有风格。而且抽象要薄——`StoreBackend` 只定义业务真正需要的 6 个方法（add_chunks/query_children/get_parent/delete_doc/list_docs/get_children_by_doc），不暴露向量维度、collection 概念、embedder。这样换 Postgres 时只映射这 6 个方法到 SQL，检索/融合/rerank 这些算法层完全不感知底层是文件还是数据库。抽象只抽象真正会变的点（存储后端），不抽象不会变的点（算法）。

- **Q：trace 为什么自建不复用项目的 reliability/trace？**
  A：reliability/trace 强耦合 runtime/workspace，RAG 是独立 Web 服务不需要那套上下文。RAG 只需要轻量 jsonl 落盘——每请求一个 trace_id，记录每步召回数/分数/耗时/降级标记，失败不抛（trace 不能影响主流程）。trace_id 生成复用了 `trace-<stamp>-<uuid6>` 风格保持一致，但实现独立。生产只打关键日志，DEBUG 模式查完整链路，所有错误必带 trace_id。

- **Q：HyDE 到底解决什么问题？什么场景用？**
  A：解决「query 和 doc 语义空间不一致」的问题。用户的问句是「问题」语义（如「怎么配置数据库」），但文档库存的是「答案」语义（如「在 config.yml 里设置 database.url 字段」）。直接用问题向量去检索答案，语义距离远。HyDE 让 LLM 先生成一个假设性答案（哪怕不准），用这个答案的向量去检索——答案和答案的语义距离更近，召回更好。适用场景：文档库大、query 和文档表述差异大的情况。坑是假设答案如果偏得太离谱会带偏检索，所以和原 query 一起多路检索再融合。

- **Q：Lost-in-the-Middle 是什么？为什么要重排？**
  A：Liu et al. 2023 的研究发现，LLM 处理长上下文时，对中间位置的信息利用率显著低于头尾——即使相关信息放在中间也会被「忽略」。所以检索回来的片段不能按相关度从前往后塞就完事。重排策略：最相关的放头、次相关的放尾、其余放中间，把最重要的信息推到 LLM 注意力高的位置。这是纯规则、零成本的操作，但效果在长上下文场景明显。

- **Q：语义缓存怎么避免返回过时答案？**
  A：两层防护。一是 TTL——每条缓存带过期时间，超时自动失效不命中（默认 1 小时）；二是语义命中阈值——余弦相似度低于阈值（默认 0.92）不算命中，避免「看似相近实则不同」的问题返回错误答案。另外文档更新时 version 变，但缓存是按 query 命中的——这是已知权衡：缓存命中返回的是旧答案。生产可以加「文档变更时清缓存」的钩子，目前没做是因为中小体量 TTL 失效已经够用。

- **Q：引用溯源怎么防 LLM 编造引用？**
  A：答案里的 `[n]` 引用必须对应上下文里真实存在的片段编号。`build_citation_refs` 会校验每个引用编号是否在 citations 范围内——LLM 如果编造一个 `[99]` 而上下文只有 5 个片段，这个引用会被丢弃，不会出现在返回的来源列表里。这保证了「溯源链」是真实的，不是 LLM 幻觉。但要注意：这只能防「引用不存在的片段」，防不了「引用了存在但无关的片段」——后者要靠 reranker 和 prompt 约束。

- **Q：Guardrails 为什么用规则不用 LLM 做二次判断？**
  A：减法原则 + fail-fast。敏感信息泄漏（API key/手机号/身份证）有明确模式，正则一抓一个准，没必要再过一遍 LLM（费 token + 慢 + LLM 自己也可能漏判）。规则 fast-path 能毫秒级拦截已知模式，只有规则覆盖不到的复杂 toxicity 场景才需要 LLM——那些留作扩展。命中护栏直接替换为拒答话术 + 记 trace 降级，是 fail-closed（安全优先）。

## 四、面试官最可能问的「设计决策」类问题

### Q：为什么用 LangGraph 而不是自己写状态机？
A：LangGraph 的 `StateGraph` + `add_messages` reducer + `stream_mode` 已经提供了状态管理、消息合并、流式输出的基础能力，不用重复造轮子。但代价是——Claude Code 自研的 `QueryEngine` 状态机能做的「StreamingToolExecutor 四态调度」「JSONL transcript 增量持久化」受 LangGraph 约束难以完全对齐。这是架构权衡，我在对齐文档里标注了这是「最大偏差」。

### Q：planner 怎么调用子 Agent 的？
A：不是直接函数调用，而是通过**工具调用**。planner 的工具列表含 `CallSearchAgentTool`/`CallCodeAgentTool`，planner 的 LLM 决定「我需要搜索」→ 产出 tool_call → Graph 层捕获执行 `run_search_agent()` → 结果作为 ToolMessage 返回。这让 LLM 自己决定什么时候需要专家，比硬编码 if-else 灵活。

### Q：三层记忆是什么？
A：
- **Rules 层**（静态）：workspace 约束、行为准则，每次都有。
- **Working Memory 层**（动态）：task/plan/todos/sources，每步更新。
- **History Summary 层**（压缩）：上下文溢出压缩后保留的长期记忆。
关键：不是把所有信息塞进 messages，而是分层存放，该在哪层在哪层。

### Q：为什么 codeAgent 用 while 而 searchAgent 用 for？
A：诚实说这是不一致。codeAgent 用 `while loops_done < max_loops` 配合 escalate 时 `loops_done -= 1`（重试不消耗迭代），searchAgent 用 `for` 循环（escalate 会消耗一次迭代）。这是待统一的技术债，不是故意设计。

### Q：工具怎么并行执行的？
A：`execute_tool_calls` 用 `ThreadPoolExecutor`，但不是所有工具都并行——`are_tools_independent` 判定工具是否只读，只读工具（FileRead/Grep/Glob）并行，mutating 工具（Bash/FileWrite）串行。这点对齐了 Claude Code 的 `isConcurrencySafe` 思想，但我目前是工具名级判定，Claude Code 是输入驱动级（`ls` 并行 / `git push` 独占），这是我列出的待对齐 Top 1（见 alignment-gaps 文档）。

### Q：BashTool 为什么是最复杂的工具？
A：它不只是执行命令，有五层机制：危险命令拦截 → 风险命令审批 → 环境准备（python/pip shims 解决「装到系统 Python 但跑的是 venv Python」问题、PATH 前置、平台适配）→ 执行（超时、输出捕获、后台模式）→ 输出处理（截断、超限落盘）。shims 是亮点——解决了 Agent 装包后 Python 解释器不一致的问题。

### Q：RAG 模块的存储抽象是怎么设计的？

A：核心是 `StoreBackend` Protocol——只定义业务真正需要的 6 个方法（add_chunks/query_children/get_parent/delete_doc/list_docs/get_children_by_doc），不暴露向量维度、collection、embedder 这些后端细节。默认 `LocalFileBackend` 用 ChromaDB 存 child 向量 + JSON 存 parent 原文，将来换 Postgres 只实现这 6 个方法映射到 SQL，检索/RRF/rerank 这些算法层零改动。抽象要薄——只抽象真正会变的点（存储后端），不抽象不会变的点（算法），这是关键。而且 `ChromaStore` 保留为门面委托 backend，service 和现有测试零改动就能跑，高级能力 opt-in。

### Q：为什么砍掉 ES 双模式？

A：因为没真实流量验证的降级路径是定时炸弹。ES 双模式意味着代码到处是 `if has_es` 分支、测试矩阵翻倍、每个 bug 查两遍，但线上跑哪种模式、另一种模式崩了能不能兜住根本没验证过。中小知识库体量 ChromaDB + BM25 内存兜底完全够用，到需要 ES 的体量再上，不搞「看起来完整但没验证」的过度设计。这正好符合我自己定的「不实现避免过度工程化」原则。

### Q：测试怎么保证的？

A：343 个测试用例覆盖核心路径，包括引擎恢复链、MCP 传输、安全分类器、记忆压缩的边界场景，以及 RAG 全链路 24 个测试（父子分块/混合检索/RRF 融合/版本控制/逻辑删除/reranker 降级/trace）。code review 发现的 bug 我都补了回归测试（比如收益递减要连续两次小增量、分类器 prompt 不抛 KeyError、handoff 不误伤工作区清理）。

## 五、会被质疑的点 + 诚实回答（预判防守）

### 质疑 1：「这不就是个套壳调 LangChain 吗？」
**回答**：LangChain 只用了最基础的 `ChatOpenAI` + `bind_tools` + 消息类型，工具执行管线、恢复链、压缩、沙箱、Hook、MCP 全是自研的。两万行代码里，真正依赖 LangChain 语义的不到 5%。选 LangChain 是因为它的消息类型和 `bind_tools` 接口成熟，不想重新发明 AIMessage/ToolMessage。我也清楚 LangChain 的抽象泄漏问题，所以引擎层 recovery 是自己包在 LangChain 调用外面的。

### 质疑 2：「和真正的 Claude Code 差距在哪？」
**回答**：诚实说，三个最大差距（都在我的对齐文档里）：

1. 没有 JSONL transcript 增量持久化 + uuid 因果链（我用的 session.json 截断数组）。
2. 没有 StreamingToolExecutor 四态状态机调度器（我用 ThreadPoolExecutor 一次性提交）。
3. 没有 ContentReplacementState 全局工具结果预算（跨轮原地替换旧大结果保 prompt cache）。

这三个受 LangGraph 状态管理约束难直接对齐，是我后续要做的事。能说出差距反而证明你真懂，不是糊弄。

### 质疑 3：「这些 code review 的 bug 是你自己发现的吗？」
**回答**：我用多 agent workflow 跑了 5 个维度的并行代码审查（引擎层/MCP/安全/记忆/编排），每条发现再用一个 skeptic agent 对抗式核实过滤误报。第一轮找到 21 条确认属实，修了 18 条；补跑两个超时维度又找到几条。这体现的是工程化的质量保证流程，不是手写代码就完美——能建立自动化审查闭环本身就是能力。

### 质疑 4：「教学向是什么意思？是不是不能用于生产？」
**回答**：教学向指代码可读性优先、注释充分、不追求极致性能优化。但工程严谨性不打折——并发安全、资源泄漏、原子写、路径校验都做了。它不能直接上生产的原因是缺 OAuth 认证、迁移系统、监控告警这些企业级基础设施，这些我在对齐文档里标注为「低价值不对齐」。

2. **被问到不懂的，说「这是我在对齐文档里标注的待对齐项」**，比硬编强。差距文档在 `docs/alignment-gaps-vs-claude-code.md`。
3. **强调你建立了自动化审查闭环**（多 agent workflow 审查），这比「我代码写得好」更有说服力——证明你有工程化的质量意识。
4. **Code review 修的那些 bug 是加分项不是减分项**——说明你能在复杂并发代码里发现并修复资源泄漏、竞态、安全问题。面试时主动讲 1-2 个最精彩的（推荐讲 SSE EOF 后传输失效 或 http hook 5xx 误阻断，这俩最能体现「静默失败」和「契约一致性」的工程敏感度）。
5. **RAG 模块要诚实讲边界**：reranker 框架完整、降级链路已验证，但真实 bge-reranker onnx 输入适配是占位实现，需拿到模型文件后补；guardrails 是规则 fast-path（正则+关键词），没做 LLM 二次 toxicity 判断（留扩展）；query_transform/answer/self_query 的 LLM 调用需配置 OpenAI env 才生效，否则全部降级——降级链路有测试覆盖。主动说这些边界比假装跑过完整 cross-encoder 更经得住深挖。讲 RAG 时重点讲「减法决策」：为什么砍 ES 双模式、为什么不用 jieba、为什么 Protocol 不用 ABC、为什么 guardrails 用规则不用 LLM——这些设计权衡比堆能力更能体现系统设计能力。
