DotAgent 权限控制系统最终设计文档（可直接交付开发）
1. 设计目标
   为 Web Coding 场景的 DotAgent 提供一套模式驱动 + 双层黑名单 + 可项目自定义扩展的安全权限体系。
   实现可控、可扩展、可审计、低侵入的工具调用权限拦截，解决 AI 自动编码、文件操作、命令执行的安全风险。
   整体遵循：系统底线不可突破、项目可追加限制、模式控制行为、禁止越权放行。
2. 系统整体架构（纯设计，无代码）
   2.1 核心组件
- PermissionManager（全局单例）
  - 全局唯一，跟随 AgentHost 生命周期
  - 维护：系统内置高危黑名单（不可覆盖、不可关闭）
  - 提供统一工具校验入口，所有工具调用必经拦截
- ProjectContext（项目维度）
  - 每个项目独立存储一套用户自定义安全规则
  - 项目打开时加载，不热更新，修改配置需重启项目生效
- Session 会话模式（会话维度）
  - 每个会话独立持有运行模式：Plan / Edit / Auto
  - 多会话隔离，互不干扰
    2.2 权限决策三态（固定）
- ALLOW：直接放行执行
- ASK：暂停任务，等待用户手动审批确认
- DENY：直接禁止，拒绝执行
3. 三级拦截优先级（绝对顺序，不可改动）
   每次工具调用，严格按以下顺序校验，前面拦截则后续逻辑直接不执行：
1. 系统内置黑名单（最高优先级，永久兜底）
2. 项目本地自定义黑名单（.agent-security.json）
3. 当前会话运行模式规则判定
   核心铁律：所有黑名单只增不减，用户配置只能加限制，不能解系统限制、不能白名单放行。
4. 三种运行模式业务语义（最终定稿）
   4.1 Plan 规划模式（纯只读）
- 只读工具（读文件、检索、查询）：ALLOW 直接放行
- 所有文件写操作（新增/编辑/删除）：ASK 需用户审批
- 所有 Bash 命令：DENY 直接禁止，不允许申请
  4.2 Edit 编辑模式（文件可改、命令受控）
- 所有文件读写删操作：ALLOW 直接放行
- 所有 Bash 命令：ASK 必须用户手动授权才可执行
  4.3 Auto 自动模式（全自动、带底线）
- 所有文件读写删：ALLOW 直接放行
- Bash 命令：默认自动放行
- 受限：命中系统黑名单 / 项目自定义黑名单的 Bash 命令依然 DENY
- Auto 模式不裸奔、不突破安全底线
5. 项目自定义配置文件规范（最终定稿）
   5.1 文件位置与加载规则
- 路径：项目根目录 .agent-security.json
- 加载时机：项目初始化打开目录时加载一次
- 不支持热更新，修改后需重启项目生效
- 文件不存在：正常运行，用户自定义规则为空
- 文件格式错误/非法 JSON：自动丢弃整套自定义规则、日志告警、不崩溃、回退系统默认规则
  5.2 固定顶层 Key（仅 2 个，不允许新增其他 Key）
  用户只能填充数组内容，不能自定义 Key、不能写放行规则、不能覆盖系统规则。
  Key 1：denyFilePatterns
- 类型：字符串数组（glob 文件路径匹配）
- 作用范围：所有文件工具（读、写、改、删）
- 语义：用户配置的保护文件/目录，Agent 完全禁止增删改查所有操作
- 只要路径命中，无论任何模式一律拦截
  Key 2：denyBashRegex
- 类型：字符串数组（正则表达式）
- 作用范围：仅 Bash 命令工具
- 语义：命中正则的命令，任何模式下直接禁止执行
  5.3 配置规范约束（强制）
- 不支持任何 allow / whiteList / enable / override 字段
- 文件中出现未知 Key 全部直接忽略，不解析、不报错
- 项目配置只能追加禁止项，不能解除系统安全限制
  5.4 标准模板示例
  {
  "denyFilePatterns": [
  "**/.env",
  "**/config/secret/**",
  "**/private/**"
  ],
  "denyBashRegex": [
  "rm\\s+-rf",
  "curl\\s+http",
  "wget\\s+http"
  ]
  }
6. 拦截提示文案规范（前端展示）
   必须区分拦截来源，方便用户排查：
- 系统拦截：该操作被系统内置安全规则禁止
- 项目配置拦截：该操作被本项目 .agent-security.json 自定义规则禁止
7. 整体执行链路终版流程
   任意工具调用触发：
1. 校验系统内置黑名单 → 命中直接 DENY
2. 校验项目自定义规则

- 文件工具 → 匹配 denyFilePatterns
- Bash 工具 → 匹配 denyBashRegex
- 命中直接 DENY
3. 读取当前会话模式（Plan/Edit/Auto）
4. 根据模式规则输出 ALLOW / ASK / DENY
5. 若为 ASK：暂停任务、保存待执行工具、等待用户确认
6. 用户确认后重新走完整校验流程，单次生效
8. 可扩展预留（本期不开发，仅预留设计）
- 未来可扩展：区分「禁止写、允许读」的细粒度文件权限 Key
- 未来可扩展：命令白名单机制、Skill 权限管控
- 未来可扩展：配置热更新
9. 开发落地结论

- 三模式核心权限逻辑
- 系统双层黑名单拦截
- 项目 JSON 双 Key 自定义禁止规则
- ASK 审批暂停/恢复链路
10. 多环境审批（ASK）交互实现方案（适配 Textual CLI/Python 最终版）
    结合项目技术栈：Python + Textual（终端富文本UI）+ FastAPI + LangGraph，对齐 Claude Code CLI 交互逻辑。废弃旧版双场景冗余逻辑，基于项目真实部署形态，定义三类标准化运行环境，完全适配本地调试、终端UI交互、线上Web服务、自动化流水线全场景。
    核心适配前提：项目依赖textual>=8.2.4，原生支持终端弹窗、富文本渲染、终端交互组件，无需原生input简陋输入，可实现媲美Web端的标准化审批弹窗交互。
    10.1 核心设计前提
    本权限体系中 ASK 审批态 是唯一需要用户人工介入的流程。基于项目技术栈特性，重构三环境分层判定逻辑，彻底解决 CLI 调试无合规审批入口、Web/终端交互不统一、自动化任务卡死的问题。
    系统固定三类运行环境（精准匹配项目部署形态）：
1. WebUI 服务环境：FastAPI 启动Web服务，前端页面交互，正式线上业务场景
2. Textual 终端UI环境：CLI 启动富文本终端（项目默认调试/本地使用形态），基于Textual组件弹窗交互
3. 纯无头自动化环境：CI/流水线、后台静默运行、无任何交互界面
   核心原则：底层权限校验、黑名单规则、模式逻辑完全统一，仅上层交互渲染逻辑差异化，一套权限内核适配全场景。
   10.2 统一基础规则（三场景通用，不可改动）
- 审批仅单次工具调用生效，无永久放行、无短时缓存放行，杜绝权限逃逸
- 用户确认/拒绝后，必须重新执行完整三级权限校验链路，规避状态篡改风险
- 审批触发场景固定：Plan模式文件写操作、Edit模式全部Bash命令
- 所有审批行为全程埋点审计，记录会话ID、工具参数、风险等级、审批结果
  10.3 环境自动识别规则（项目专属）
  系统启动自动判定运行环境，优先级从高到低，无人工配置，全自动适配：
1. FastAPI Web服务已启动、存在前端会话连接 → WebUI环境
2. CLI启动、Textual应用实例正常挂载（终端富文本环境） → Textual终端UI环境（核心调试/日常使用场景）
3. 无Web服务、无Textual交互实例、无头参数/CI环境 → 纯自动化无头环境
   10.4 三类环境审批技术实现方案（适配Python+Textual）
   10.4.1 WebUI 环境（线上正式业务）
   处理逻辑：挂起LangGraph任务 + 前端自定义审批弹窗
1. 权限校验命中 ASK，不执行工具、不终止任务
2. 缓存待执行工具名、脱敏参数、风险说明、拦截来源至Session会话状态
3. 暂停LangGraph执行链路，向前端推送审批事件
4. 前端渲染标准化审批弹窗，展示完整风险信息
5. 用户点击【确认执行/拒绝取消】后，后端携带人工确认标记恢复任务
6. 重走完整三级权限校验链路，执行或终止工具调用，清空缓存状态
   10.4.2 Textual 终端UI环境（本地调试/CLI核心场景，项目专属）
   处理逻辑：Textual原生弹窗组件 + 终端阻塞交互（对标 Claude Code CLI 审批体验）
   废弃简陋原生input输入，依托项目自带Textual依赖，实现终端标准化弹窗审批，和Web体验对齐，是本地开发、功能测试的核心方案。
1. 权限校验命中 ASK 状态
2. 调用Textual模态弹窗组件，在终端富文本界面渲染审批面板
3. 弹窗固定展示信息：当前Agent模式、操作类型、脱敏操作内容、风险等级、拦截规则来源
4. 提供交互式按钮：【确认执行】【拒绝取消】
5. 阻塞当前任务链路，等待用户终端点击操作
6. 用户确认：携带审批标记重走权限链路，放行执行；用户拒绝：直接终止本次工具调用
   终端弹窗标准化文案：复刻专业CLI智能体体验，简洁清晰、风险明确
   【权限审批确认】运行模式：xxx | 风险操作：xxx | 规则来源：系统/项目自定义规则
   请确认是否执行本次操作？
   10.4.3 纯无头自动化环境（CI/后台/静默任务）
   处理逻辑：无交互、自动兜底拒绝，不阻塞整体任务链路
- 无Web界面、无Textual终端交互能力，完全无人值守
- ASK状态统一自动降级为DENY，终止单次风险操作，不挂起、不卡死任务
- 输出标准化日志，记录拦截原因，方便自动化运维排查
  标准化日志文案：当前操作需人工审批，当前为无头自动化运行环境，自动拦截本次操作

- 系统内置黑名单、项目自定义黑名单拦截的高危操作，任何场景、任何人工确认都无法放行，安全底线永久不突破
- 统一解决旧方案缺陷：本地CLI调试无正规审批入口、体验简陋、无法完整测试ASK权限链路
  10.1 核心设计前提（修正版，支持调试交互）

   10.4 三种环境审批实现方案
   10.4.1 WebUI 环境（正式业务）
   处理逻辑：挂起任务 + 前端弹窗审批
1. 权限校验命中 ASK，不执行工具、不终止任务

4. 用户点击【确认/拒绝】后恢复任务，重走权限校验
   10.4.2 控制台调试环境（本地开发/测试，重点新增）
   处理逻辑：阻塞终端 + 启用 input 交互式审批（解决本地调试无法测试ASK流程的问题）
   这是本次修正的核心：无WebUI不直接拒绝，而是让开发者在控制台手动输入确认
1. 权限校验命中 ASK
2. 控制台打印标准化风险提示：当前模式、待执行操作、风险说明
3. 阻塞任务，调用终端输入逻辑，等待用户输入：[Y/N] 确认是否执行本次操作？
4. 输入 Y：放行，携带确认标记重走权限流程执行工具
5. 输入 N：拒绝，终止本次工具调用
   控制台标准输出文案：
   【权限审批需人工确认】运行模式：xxx | 待操作：xxx | 风险操作需手动确认，输入 Y 执行 / N 取消
   10.4.3 纯无头自动化环境（CI/后台/流水线）

- 打印日志提示，不卡死、不挂起任务，保证自动化流程稳定
