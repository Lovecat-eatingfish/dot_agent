# dot_agent 项目阅读指南

> 本文档帮助你快速理解项目的核心架构、数据流和关键模块，适合从零开始阅读代码。

---

## 一、项目一句话概括

**dot_agent 是一个基于 LangGraph 的多智能体 CodeAgent 系统**，核心流程是：

```text
用户输入 → 意图识别 → 任务规划 → 工具执行 → 结果验证 → 输出
                          ↑                    ↓
                          └──── 失败重试 ─────┘
```

## 二、推荐阅读顺序

### 第一步：理解入口和数据流

| 顺序 | 文件 | 看什么 |
| --- | --- | --- |
| 1 | `src/mokioclaw/interaction/app.py` | CLI 入口，理解 `mokioclaw "task"` 怎么触发 |
| 2 | `src/mokioclaw/orchestration/agent.py` | `stream_agent_events()` 是核心调度器，连接 CLI 和 LangGraph |
| 3 | `src/mokioclaw/orchestration/workflow.py` | LangGraph 图定义，看节点和边的关系 |

**关键数据流：**

```text
app.py: main()
  → stream_agent_events(task)          # agent.py
    → build_entry_workflow()           # workflow.py - 意图路由
    → build_complex_workflow()         # workflow.py - 任务执行
      → planner_node → code_agent_node → verifier_node → ...
```

### 第二步：理解状态系统

| 文件 | 看什么 |
| --- | --- |
| `src/mokioclaw/state/graph.py` | `MokioGraphState` - 所有节点共享的全局状态 |
| `src/mokioclaw/state/runtime.py` | `RuntimeState` - 运行时配置（工作区、安全、审批） |

**核心概念：**

- `MokioGraphState` 是 LangGraph 的状态容器，所有节点通过读写它来通信
- `RuntimeState` 是运行时配置，贯穿整个执行生命周期
- 状态字段用 `Annotated[list, add_messages]` 做自动合并

### 第三步：理解节点实现

| 文件 | 看什么 |
| --- | --- |
| `src/mokioclaw/orchestration/nodes.py` | 所有节点的实现（planner、verifier、context_monitor 等） |
| `src/mokioclaw/agents/code_agent.py` | codeAgent 的具体执行逻辑 |
| `src/mokioclaw/agents/search_agent.py` | searchAgent 的 Tavily 搜索逻辑 |

**节点职责：**

- `planner_node`: 分析任务，生成计划，决定路由（search/code/verify/final）
- `code_agent_node`: 执行文件操作、bash 命令
- `search_agent_node`: 调用 Tavily 搜索
- `verifier_node`: 只读校验任务是否完成
- `context_monitor_node`: 监控 token 用量，决定是否压缩
- `context_compressor_node`: 执行上下文压缩

### 第四步：理解工具系统

| 文件 | 看什么 |
| --- | --- |
| `src/mokioclaw/tools/registry.py` | 工具注册、并发安全元数据 |
| `src/mokioclaw/tools/bash_tool.py` | 最复杂的工具，包含危险检测、审批、平台适配 |
| `src/mokioclaw/tools/file_tools.py` | 文件读写工具的实现模式 |

**工具约定：**

- 所有工具返回结构化结果：`{ok: bool, error: str, error_message: str, hint: str}`
- 并发安全通过 `TOOL_CONCURRENCY_META` 声明
- 安全工具（只读）可并行，不安全工具（写入）必须串行

### 第五步：理解记忆和压缩

| 文件 | 看什么 |
| --- | --- |
| `src/mokioclaw/memory/memory.py` | 三层记忆系统的组装 |
| `src/mokioclaw/memory/dual_threshold_compression.py` | 双阈值压缩策略 |
| `src/mokioclaw/memory/tiered_compression.py` | 消息分级压缩（KEEP/COMPRESS/DROP） |

**三层记忆：**

```text
rules（规则层）         → 跨任务持久化，来自 CLAUDE.md / config.md
working_memory（工作记忆）→ 当前任务的计划、待办、研究笔记
history_summary_store    → 历史对话的压缩摘要
```

**压缩策略：**

- 软阈值（70%）：异步预生成摘要
- 硬阈值（90%）：同步强制压缩，保留最近 10 条消息 + 旧摘要

### 第六步：理解配置系统

| 文件 | 看什么 |
| --- | --- |
| `src/mokioclaw/config/loader.py` | YAML frontmatter + markdown body 的解析 |
| `.mokioclaw/config.md.example` | 配置文件格式示例 |

**配置优先级（后者覆盖前者）：**

```text
默认值 → ~/.mokioclaw/CLAUDE.md（全局） → .mokioclaw/config.md（项目） → CLAUDE.md（工作区）
```

## 四、关键设计模式

### 1. 状态驱动而非返回值驱动

节点不直接返回值给下一个节点，而是写入 `MokioGraphState`，下一个节点从状态中读取：

```python
# planner_node 写入状态
return {"planner_route": "code", "plan_summary": "..."}

# code_agent_node 从状态读取
route = state.get("planner_route")
```

### 2. 工具并发安全声明

```python
# registry.py
TOOL_CONCURRENCY_META = {
    "FileReadTool": True,    # 只读，可并行
    "BashTool": False,       # 有副作用，必须串行
    "TodoUpdateTool": False, # 有竞态风险，必须串行
}
```

### 3. 结构化错误返回

所有工具统一返回格式，从不抛异常：

```python
return {"ok": False, "error": "file_not_found", "error_message": "文件不存在", "hint": "检查路径"}
```

### 4. 事件总线解耦

```python
# 发布事件
event_bus.emit({"type": "tool_result", "tool": "bash", "output": "..."})

# 订阅事件（TUI、CLI、checkpoint 各自订阅）
event_bus.subscribe("tool_result", tui_handler)
```

## 九、为什么要这样设计？（设计决策背后的思考）

### 1. 为什么用多 Agent 而不是单 Agent？

**问题**：单 Agent 要同时扮演规划者、执行者、验证者，prompt 会变得又长又混乱，LLM 容易迷失角色。

**解决方案**：拆成专职 Agent，每个 Agent 只做一件事：

- **planner**：只负责思考"下一步该做什么"，不碰文件
- **codeAgent**：只负责执行，不负责规划
- **verifier**：只负责检查，不负责修改

**好处**：

- 每个 Agent 的 prompt 更短、更聚焦，LLM 输出质量更高
- planner 可以用不同的工具调用不同的 Agent，像项目经理分配任务
- verifier 独立于 codeAgent，不会"自己改自己查"

**代价**：

- 多了一层 LLM 调用（planner 决定调谁），增加延迟
- Agent 之间通过状态通信，调试时要跨文件看

---

### 2. 为什么用 LangGraph 而不是自己写循环？

**问题**：自己写 `while` 循环管理 Agent 调用，会遇到：

- 条件路由逻辑散落在各处
- 状态管理容易出错
- 重试、压缩、验证的跳转逻辑变得复杂

**LangGraph 的优势**：

- **声明式图定义**：节点和边的关系一目了然
- **内置状态管理**：`add_messages` reducer 自动合并消息列表
- **条件路由**：`add_conditional_edges` 让分支逻辑集中在一处
- **可视化**：可以画出流程图，方便理解和调试

```python
# 自己写循环（难维护）
while not passed:
    plan = planner(task)
    result = code_agent(plan)
    passed = verifier(result)
    if attempts > max: break

# LangGraph（声明式）
graph.add_edge("planner", "code_agent")
graph.add_edge("code_agent", "verifier")
graph.add_conditional_edges("verifier", route_fn, {"passed": "final", "failed": "planner"})
```

---

### 3. 为什么要三层记忆？全部放 messages 不行吗？

**问题**：LLM 有上下文窗口限制（比如 128K tokens）。如果把所有历史消息都塞进去：

- 很快就会超限
- 旧消息里的噪音会干扰 LLM 判断
- 每次都要重新发送所有消息，浪费 token

**三层记忆的设计**：

| 层级 | 放什么 | 为什么这样分 |
| --- | --- | --- |
| **rules** | 行为准则、工作区约束 | 每次都要有，不变，放 prompt 里 |
| **working_memory** | 当前任务的计划、待办、研究笔记 | 当前任务需要，每步更新 |
| **history_summary** | 历史对话的压缩摘要 | 跨任务保留，但不占用太多 token |

**关键洞察**：

- LLM 不需要看到第 1 轮的完整对话，只需要知道"之前做了什么"
- 通过压缩，把 O(n²) 的全量重算变成 O(n) 的增量叠加
- 原始历史持久化到 `RAW_HISTORY.md`，需要时可以回溯

---

### 4. 为什么是双阈值压缩（70% 和 90%）？

**问题**：只在超限时压缩（比如 100%），会导致：

- 压缩是同步阻塞的，用户要等很久
- 压缩质量可能不好（LLM 赶时间）

**双阈值策略**：

```text
0% ─────────── 70% ─────────── 90% ─────────── 100%
                │                │
                │ 软阈值          │ 硬阈值
                │ 异步预生成摘要   │ 同步强制压缩
                │ 不阻塞          │ 阻塞但保证不超限
```

**为什么是 70% 和 90%？**

- 70%：留出足够缓冲，异步生成的摘要可以提前准备好
- 90%：保证在超限前完成压缩，给 LLM 留点余量处理压缩本身
- 如果只设一个阈值（比如 80%），要么太早压缩浪费资源，要么太晚压缩来不及

---

### 5. 为什么工具要声明并发安全？

**问题**：Agent 可能同时调用多个工具。如果两个工具同时写同一个文件，会出问题。

**解决方案**：在 `registry.py` 里声明每个工具的安全性：

```python
TOOL_CONCURRENCY_META = {
    "FileReadTool": True,    # 只读，可以并行
    "GlobTool": True,        # 只读，可以并行
    "BashTool": False,       # 可能写文件，必须串行
    "TodoUpdateTool": False, # 写同一个文件，必须串行
}
```

**为什么不让所有工具都串行？**

- 只读工具（FileRead、Glob、Grep）并行可以显著提速
- 比如 Agent 同时读 3 个文件，并行只需要 1 次 LLM 调用的时间

**为什么不让所有工具都并行？**

- BashTool 可能执行 `rm`、`mv` 等操作，并行会冲突
- TodoUpdateTool 写同一个 `TODO.md`，并行会覆盖

---

### 6. 为什么工具返回结构化错误而不是抛异常？

**问题**：如果工具抛异常，Agent 的工具调用循环会中断，LLM 看不到有用的错误信息。

**结构化错误的好处**：

```python
# 抛异常（不好）
raise FileNotFoundError("file not found")  # Agent 循环中断

# 结构化返回（好）
return {"ok": False, "error": "file_not_found", "error_message": "文件不存在", "hint": "检查路径"}
# Agent 可以看到错误，决定下一步（比如换个路径重试）
```

**为什么要有 `error` 和 `error_message` 两个字段？**

- `error`：机器可读的错误码，Agent 可以用来做逻辑判断
- `error_message`：人类可读的描述，方便调试

**为什么要有 `hint`？**

- 给 Agent 一个"下一步建议"，减少无效重试
- 比如 "hint": "检查路径是否正确" 比让 Agent 自己猜更高效

---

### 7. 为什么用 EventBus 而不是直接调用？

**问题**：如果节点直接调用渲染函数，会导致：

- 图层（orchestration）依赖交互层（interaction）
- 换一种渲染方式（Rich → TUI）要改节点代码
- 多个消费者（TUI、checkpoint、trace）要串行调用

**EventBus 的解耦**：

```python
# 节点只负责发事件
event_bus.emit({"type": "tool_result", "tool": "bash", "output": "..."})

# 消费者各自订阅，互不影响
event_bus.subscribe("tool_result", tui_handler)      # TUI 更新界面
event_bus.subscribe("tool_result", checkpoint_handler) # 保存检查点
event_bus.subscribe("tool_result", trace_handler)      # 记录追踪
```

**好处**：

- 节点不知道也不关心谁在监听
- 添加新消费者（比如日志系统）不需要改节点代码
- 消费者可以独立启用/禁用

---

### 8. 为什么 planner 通过工具调用 Agent 而不是直接函数调用？

**问题**：如果 planner 直接调用 `run_code_agent()`，planner 的 LLM 就无法决定"什么时候需要调用"。

**工具调用的好处**：

```python
# 直接函数调用（planner 无法控制）
def planner_node(state):
    result = run_code_agent(state, "写文件")  # 硬编码调用
    return result

# 工具调用（planner 的 LLM 自己决定）
planner_tools = [CallCodeAgentTool(), CallSearchAgentTool(), TodoWriteTool()]
# LLM 看到任务后，自己决定："我需要先搜索，再写代码"
# → tool_call: CallSearchAgent(instruction="搜索快速排序算法")
# → tool_call: CallCodeAgent(instruction="实现快速排序")
```

**关键洞察**：

- planner 的 LLM 比硬编码逻辑更灵活
- LLM 可以根据任务复杂度决定是否需要搜索、需要几次代码调用
- 工具调用的结果作为 `ToolMessage` 返回，LLM 可以据此调整计划

---

### 9. 为什么 verifier 只能用只读工具？

**问题**：如果 verifier 能修改文件，它可能会：

- 自己改了代码，然后说"通过了"
- 掩盖 codeAgent 的错误

**只读约束的好处**：

- verifier 真正扮演"测试员"角色：只能看，不能改
- 如果验证失败，必须回到 planner → codeAgent 去修复
- 保证了验证的客观性

```python
# verifier 的工具集
build_read_only_tools()  # 只有 FileRead、Grep、Bash（只读模式）、WebSearch
                         # 没有 FileWrite、FileEdit、TodoUpdate
```

---

### 10. 为什么要有意图路由（chat vs workflow）？

**问题**：用户可能只是想聊天（"今天天气怎么样"），不需要启动完整的任务执行流程。

**意图路由的好处**：

- 轻量聊天直接回复，不需要规划、工具调用、验证
- 节省 token 和时间
- 用户体验更好（聊天秒回，任务要等）

```python
# 意图路由逻辑
if intent == "chat":
    → chat_responder（直接用 LLM 回复，不用工具）
elif intent == "workflow":
    → planner（启动完整任务流程）
```

---

### 11. 为什么 BashTool 要有 shims 目录？

**问题**：Agent 运行 `pip install requests` 时，可能装到了系统 Python，但后面 `python app.py` 用的是虚拟环境的 Python。

**shims 的解决方案**：

```python
# .mokioclaw/shims/python → 指向 .venv/bin/python
# .mokioclaw/shims/pip → 指向 .venv/bin/pip

# BashTool 执行命令前，把 shims 目录加到 PATH 最前面
env["PATH"] = str(shims_dir) + ":" + env["PATH"]
```

**好处**：

- Agent 的 `python` 和 `pip` 始终指向同一个虚拟环境
- 避免"装了但用不了"的问题
- 跨平台统一（Windows 的 python vs python3 问题也解决了）

---

### 12. 为什么检查点要区分 light 和 strict 模式？

**问题**：完整保存 LangGraph 状态（strict 模式）很慢，而且状态可能很大。

**两种模式的权衡**：

| 模式 | 保存内容 | 恢复方式 | 适用场景 |
| --- | --- | --- | --- |
| **light** | checkpoint.json + RECOVERY.md + git 快照 | 读恢复文档，重新进入 workflow | 大多数场景，快 |
| **strict** | 额外保存 state.json + events.jsonl | 尝试反序列化 state | 需要精确恢复时 |

**为什么默认用 light？**

- 保存快（几百毫秒 vs 几秒）
- 恢复时重新执行 planner，可能得到更好的计划（因为有更多上下文）
- git 快照保证文件状态可恢复

**什么时候用 strict？**

- 任务执行了很久，不想重新规划
- 需要精确恢复到某个节点的状态

---

### 13. 为什么配置用 YAML frontmatter + markdown body？

**问题**：纯 YAML 配置文件不支持长文本指令；纯 markdown 配置文件不支持结构化字段。

**混合格式的好处**：

```markdown
---
approval_mode: inline        # ← 结构化配置（YAML）
max_attempts: 5
bash_timeout: 300
---

# Custom Instructions           # ← 自由文本指令（markdown）

以下指令会注入到所有 agent 的 system prompt 中：
- Always add type hints to Python code
- Use async/await for I/O operations
```

**为什么不用 JSON？**

- JSON 不支持注释
- JSON 的长文本很难维护

**为什么不用纯 YAML？**

- YAML 的多行文本语法不直观
- markdown body 可以用标题、列表、代码块，更适合写指令

## 十、设计模式总结

| 模式 | 解决的问题 | 体现位置 |
| --- | --- | --- |
| 多 Agent 编排 | 单 Agent prompt 太长、角色混乱 | workflow.py + agents/ |
| 状态驱动 | 节点间通信耦合 | MokioGraphState |
| 工具并发声明 | 并行执行冲突 | registry.py |

| 三层记忆 | 上下文窗口限制 | memory/ |
| 双阈值压缩 | 压缩时机和质量 | dual_threshold_compression.py |
| 只读验证 | 验证客观性 | verifier_node |
| 意图路由 | 聊天 vs 任务分流 | intent_router_node |
| shims 目录 | 工具链一致性 | bash_tool.py |
