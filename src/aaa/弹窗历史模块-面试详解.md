# 弹窗历史模块 — 面试详解

> 用途：面试时讲清楚弹窗历史模块的技术实现
> 定位：你在这个项目中负责/参与的核心模块之一

## 一、业务背景

### 产品需求

运营需要在 APP 内展示各种弹窗（折扣、推荐、登录引导等），但有几个问题需要解决：

1. **频控问题**：用户抱怨弹窗太多，影响体验 → 需要限制每日弹窗次数
2. **轮换问题**：每次弹同一个弹窗，用户麻木 → 需要按优先级轮换展示
3. **数据问题**：不知道弹窗效果如何 → 需要记录每次弹窗展示的数据

### 我负责的部分

**用户弹窗历史模块**，核心职责：
1. 记录每次弹窗展示的完整上下文
2. 实现每日弹窗次数限制（频控）
3. 为弹窗轮询机制提供数据支持

## 三、频控逻辑实现

### 需求

运营在后台配置弹窗规则时，可以设置**每日弹出次数**（popupCount）：
- popupCount = 0 → 不限制
- popupCount = 3 → 每天最多弹 3 次

### 实现代码

```java
// 1. 查询用户当天的弹窗历史
List<PopupUserHistoryDAO> popupHistoryList = popupUserHistoryRepository.lambdaQuery()
    .eq(PopupUserHistoryDAO::getUserId, userId)
    .ge(PopupUserHistoryDAO::getCreateTime, DateUtil.beginOfDay(requestTime))  // 当天 00:00:00
    .le(PopupUserHistoryDAO::getCreateTime, DateUtil.endOfDay(requestTime))    // 当天 23:59:59
    .in(PopupUserHistoryDAO::getPopupRuleId, popupRuleIdList)
    .list();

// 2. 按规则ID分组统计次数
Map<Long, Long> popupHistoryCountMap = popupHistoryList.stream()
    .collect(Collectors.groupingBy(
        PopupUserHistoryDAO::getPopupRuleId, 
        Collectors.counting()
    ));

// 3. 过滤超过次数限制的规则
popupRuleList = popupRuleList.stream()
    .filter(e -> {
        // 0 代表不限制次数
        if (e.getPopupCount() == 0) {
            return true;
        }
        Long popupRuleId = e.getId();
        Long count = popupHistoryCountMap.get(popupRuleId);
        if (count == null) {
            return true;  // 今天没弹过
        }
        return count < e.getPopupCount();  // 未超限
    })
    .collect(Collectors.toList());
```

### 执行流程

```
用户请求弹窗
    │
    ▼
查询当天的弹窗历史
(user_id=123 AND create_time BETWEEN 今天00:00 AND 今天23:59)
    │
    ▼
按 popup_rule_id 分组统计
rule_1: 2次
rule_2: 3次
rule_3: 0次
    │
    ▼
过滤超过限制的规则
假设 rule_1 的 popupCount=3 → 2 < 3 → 保留 ✅
假设 rule_2 的 popupCount=2 → 3 >= 2 → 过滤 ❌
假设 rule_3 的 popupCount=0 → 不限制 → 保留 ✅
    │
    ▼
只返回未超限的规则
```

### 面试追问

**Q: 为什么按天统计而不是按小时？**
> 业务需求是"每日弹窗次数"，不是"每小时"。如果按小时统计，用户一天内可能看到很多次弹窗，体验不好。

**Q: 为什么用 create_time 而不是 request_time？**
> create_time 是记录入库时间，request_time 是前端传的请求时间。为了保证一致性，用 create_time 更可靠，不受前端时间不准的影响。

**Q: 查询性能怎么样？**
> 走了 `idx_user_date` 联合索引（user_id + create_time），查询很快。而且只查当天的数据，数据量很小。

**Q: 如果用户跨天了怎么办？**
> 每次查询都是基于当前时间计算当天的起止时间，跨天后自动重新计数。比如用户 23:59 弹了 1 次，00:01 再请求，会查新的一天，count 重新从 0 开始。

## 四、轮询逻辑实现

### 需求

每次弹窗请求只返回 1 个弹窗，按优先级轮换展示，避免每次弹同一个。

### 实现代码

```java
// 1. 按优先级排序（数字越小优先级越高）
popupList.sort((e1, e2) -> {
    int sortCompare = e1.getSort().compareTo(e2.getSort());
    if (sortCompare != 0) {
        return sortCompare;
    }
    return e2.getPopupRuleId().compareTo(e1.getPopupRuleId());
});

// 2. 查询上次展示的弹窗
PopupUserHistoryDAO lastPriorityRecord = popupUserHistoryRepository.lambdaQuery()
    .select(PopupUserHistoryDAO::getPriority, PopupUserHistoryDAO::getPopupRuleId)
    .eq(PopupUserHistoryDAO::getUserId, userId)
    .eq(PopupUserHistoryDAO::getPosition, queryDTO.getPosition())      // 同位置
    .eq(PopupUserHistoryDAO::getTriggerTiming, queryDTO.getTriggerTiming()) // 同时机
    .orderByDesc(PopupUserHistoryDAO::getId)
    .last("limit 1")
    .one();

// 3. 找到优先级比上次高的下一个弹窗
Integer lastPriority = lastPriorityRecord.getPriority();
AppPopupInfoVO resultPopupInfoVO = null;
for (AppPopupInfoVO popupInfoVO : popupList) {
    // 找到优先级比上次高的，且不是同一个规则
    if (!Objects.equals(popupInfoVO.getPopupRuleId(), lastPriorityRecord.getPopupRuleId()) &&
            popupInfoVO.getSort() > lastPriority) {
        resultPopupInfoVO = popupInfoVO;
        break;
    }
}

// 4. 如果没有更高的，回到第一个（循环）
if (resultPopupInfoVO == null) {
    resultPopupInfoVO = popupList.get(0);
}

// 5. 只返回这一个弹窗
popupList = new ArrayList<>(Collections.singleton(resultPopupInfoVO));
```

### 执行流程

```
假设有 3 个弹窗，优先级分别是 1、2、3

第 1 次请求：
├── 上次记录：无
├── 直接取第一个：优先级 1
└── 返回：弹窗 A（优先级 1）

第 2 次请求：
├── 上次记录：优先级 1
├── 找优先级 > 1 的：优先级 2
└── 返回：弹窗 B（优先级 2）

第 3 次请求：
├── 上次记录：优先级 2
├── 找优先级 > 2 的：优先级 3
└── 返回：弹窗 C（优先级 3）

第 4 次请求：
├── 上次记录：优先级 3
├── 找优先级 > 3 的：无
├── 回到第一个：优先级 1
└── 返回：弹窗 A（优先级 1）

循环往复...
```

### 面试追问

**Q: 为什么要轮询而不是每次都弹优先级最高的？**
> 如果每次都弹优先级最高的，用户会一直看到同一个弹窗，体验不好。轮询可以让用户看到不同的弹窗，提升转化率。

**Q: 测试弹窗和正式弹窗怎么处理？**
> 测试弹窗优先于正式弹窗。如果有测试弹窗，直接返回测试弹窗，不参与轮询逻辑。

**Q: 怎么保证同一个位置、同一个时机的弹窗轮换？**
> 查询历史记录时加了 `position` 和 `triggerTiming` 条件，只查同位置、同时机的历史记录。这样不同位置的弹窗互不影响。

**Q: 如果用户清除了应用数据怎么办？**
> 历史记录存在服务端数据库，不受客户端影响。用户清除应用数据后，历史记录还在，频控和轮询继续生效。

## 五、历史记录保存

### 保存时机

每次弹窗展示时，在返回给 APP 之前保存历史记录。

### 保存代码

```java
List<PopupUserHistoryDAO> historyList = new ArrayList<>(popupList.size());
for (AppPopupInfoVO popupInfoVO : popupList) {
    PopupUserHistoryDAO history = new PopupUserHistoryDAO();
    
    // 基础信息
    history.setUserId(userId);
    history.setPopupRuleId(popupInfoVO.getPopupRuleId());
    history.setPopupId(popupInfoVO.getPopupId());
    history.setIsTest(popupInfoVO.getRule().getIsTest());
    
    // 触发信息
    history.setTriggerType(popupInfoVO.getRule().getTriggerType());
    history.setPosition(popupInfoVO.getRule().getPosition());
    history.setTriggerTiming(popupInfoVO.getRule().getTriggerTiming());
    
    // 用户上下文
    history.setPlayId(queryDTO.getPlayId());
    history.setSeriesId(queryDTO.getSeriesId());
    history.setStoreCountryCode(queryDTO.getStoreCountryCode());
    history.setPlaySecondTime(queryDTO.getPlaySecondTime());
    
    // 弹窗信息
    history.setPopupType(popupInfoVO.getPopupType());
    history.setPopupName(popupInfoVO.getRule().getPopupName());
    history.setPriority(popupInfoVO.getSort());
    
    // 会话信息
    history.setSessionId(sessionId);
    history.setRequestTime(requestTime);
    history.setCreateTime(createTime);
    
    // 推荐弹窗：记录推荐的剧集信息
    if (popupInfoVO.getPopupType().equals(PopupConstants.PopupType.PLAY_RECOMMEND.getCode())) {
        PlayRecommendPopupVO playParam = (PlayRecommendPopupVO) popupInfoVO.getParam();
        Map<String, Long> playInfoMap = new HashMap<>();
        for (PlayRecommendItemVO playInfo : playParam.getPlays()) {
            playInfoMap.put("play_id", playInfo.getPlayId());
            playInfoMap.put("series_id", playInfo.getSeriesId());
        }
        history.setPlayInfo(JSONObject.toJSONString(playInfoMap));
    }
    
    // 折扣弹窗：记录三方支付信息
    if (popupInfoVO.getPopupType().equals(PopupConstants.PopupType.DISCOUNT.getCode())) {
        GoodsDiscountPopupVO goodsDiscountParam = (GoodsDiscountPopupVO) popupInfoVO.getParam();
        history.setIsThirdParty(goodsDiscountParam.getTpShow() ? 1 : 0);
        history.setAvailablePayment(JSONObject.toJSONString(goodsDiscountParam.getPmList()));
    }
    
    historyList.add(history);
}

// 批量保存
popupUserHistoryRepository.saveBatch(historyList);
```

### 面试追问

**Q: 为什么要记录 playInfo 和 availablePayment？**
> - playInfo：推荐弹窗展示的剧集列表，用于分析推荐准确率（用户是否点击了推荐的剧）
> - availablePayment：折扣弹窗展示的支付方式，用于分析用户支付偏好（哪种支付方式转化率高）

**Q: sessionId 是什么？**
> 前端传的会话 ID，格式是 `{timestamp}_{deviceId}`。用于追踪用户的一次完整使用过程，比如用户打开 APP → 看到弹窗 → 点击 → 跳转 → 支付，整个链路可以通过 sessionId 串联。

**Q: 为什么要区分 requestTime 和 createTime？**
> - requestTime：前端传的请求时间，可能不准确（用户手机时间不准）
> - createTime：服务端入库时间，准确
> 两者对比可以发现客户端时间异常，用于数据清洗

## 八、面试问答模板

### Q: 介绍一下弹窗历史模块

> 弹窗历史模块是弹窗系统的核心支撑模块，主要解决三个问题：
>
> **1. 频控**：限制用户每天看到的弹窗次数，防止骚扰。实现方式是查询用户当天的历史记录，按规则分组统计次数，超过限制的规则不再弹出。
>
> **2. 轮询**：每次只返回一个弹窗，按优先级轮换展示。实现方式是查询用户上次展示的弹窗优先级，找到优先级比上次高的下一个弹窗，如果没有更高的就回到第一个，实现循环。
>
> **3. 数据采集**：记录每次弹窗展示的完整上下文，包括用户信息、弹窗信息、触发场景、业务信息等，用于效果分析和问题排查。

### Q: 频控是怎么实现的？

> 频控的实现分三步：
> 1. 查询用户当天的弹窗历史（userId + 当天时间范围）
> 2. 按 popupRuleId 分组统计每个规则的弹窗次数
> 3. 过滤掉超过 popupCount 限制的规则
>
> 关键点是用了 userId + create_time 的联合索引，查询性能很好。而且只查当天的数据，数据量很小。

### Q: 轮询是怎么实现的？

> 轮询的实现分四步：
> 1. 按优先级排序（数字越小优先级越高）
> 2. 查询用户上次展示的弹窗（同位置、同时机）
> 3. 找到优先级比上次高的下一个弹窗
> 4. 如果没有更高的，回到第一个（循环）
>
> 测试弹窗始终优先于正式弹窗，不参与轮询逻辑。

### Q: 为什么需要 popup_user_history 表？

> 三个原因：
> 1. **频控**：需要查询用户当天已弹次数，必须有历史记录
> 2. **轮询**：需要查询用户上次展示的弹窗，必须有历史记录
> 3. **数据分析**：需要记录每次弹窗展示的效果，必须有历史记录
>
> 如果没有这个表，频控和轮询都无法实现，用户体验会很差。

### Q: 历史记录的数据量大了怎么办？

> 目前没有做分表，因为查询都是带 userId 条件的，走了索引，性能还可以。
>
> 如果未来数据量增长，可以考虑：
> 1. **定期归档**：把 3 个月前的历史数据迁移到归档表
> 2. **按时间分表**：按月分表，查询时指定表名
> 3. **只保留必要字段**：playInfo、availablePayment 这些 JSON 字段可以压缩或拆分
>
> 但目前来看，弹窗历史的数据量不会太大，因为有频控限制，每个用户每天最多弹几次。

### Q: 怎么保证数据一致性？

> 历史记录的保存是在弹窗返回给 APP 之前，用 saveBatch 批量保存的。如果保存失败，整个事务会回滚，弹窗也不会返回给 APP。
>
> 这样保证了：如果 APP 收到了弹窗，历史记录一定保存成功；如果保存失败，APP 不会收到弹窗。

## 九、可能被深挖的点

### Q: 如果用户同时发多个弹窗请求怎么办？

> 会有并发问题。比如用户快速刷新页面，可能同时发出多个请求，每个请求都查询历史记录，都发现未超限，然后都返回弹窗，导致实际弹窗次数超过限制。
>
> 解决方案：
> 1. **乐观锁**：在历史记录表加 version 字段，更新时检查版本
> 2. **分布式锁**：用 Redis 锁住 userId，同一时间只处理一个请求
> 3. **忽略**：弹窗频控不是强一致性的需求，偶尔超限 1-2 次可以接受
>
> 我们目前用的是方案 3，因为弹窗频控不是强一致性需求。

### Q: 如果用户换设备了怎么办？

> 弹窗历史是按 userId 存储的，不是按 deviceId。用户换设备登录后，历史记录还在，频控继续生效。
>
> 这样设计是合理的，因为频控的目的是防止骚扰用户，而不是骚扰设备。

### Q: 如果用户退出登录了怎么办？

> 退出登录后，userId 变了（变成新用户），历史记录查不到了，频控重新开始。
>
> 这是合理的设计，因为新用户应该有新的弹窗策略。

### Q: 推荐弹窗的 playInfo 字段存的是什么？

> 存的是推荐的剧集列表，格式是 JSON：
> ```json
> {
>     "play_id": 123,
>     "series_id": 456
> }
> ```
>
> 用于分析推荐准确率：用户看到推荐弹窗后，是否点击了推荐的剧集。

### Q: 折扣弹窗的 availablePayment 字段存的是什么？

> 存的是可用的支付方式列表，格式是 JSON：
> ```json
> [
>     {"payMethod": 0, "payPlatform": 0, "sort": 1},  // Stripe
>     {"payMethod": 1, "payPlatform": 1, "sort": 2}   // PayPal
> ]
> ```
>
> 用于分析用户支付偏好：哪种支付方式的转化率最高。
