## 第一部分：项目描述（开场白）

### 面试官："介绍一下你做的这个项目"

**标准回答：**

> 我在一个全球化短剧流媒体平台实习，这个平台面向海外 14 个国家的用户。我主要负责消息推送模块，包括三个子系统：
>
> 第一是 **App 推送**，基于 Firebase Cloud Messaging 实现，支持两种模式：一种是 Token 精准推送，针对指定用户群；另一种是 Topic 广播，按语言群发给所有订阅用户。
>
> 第二是 **邮件推送**，通过 AWS SQS 消息队列异步处理，最终调用 AWS SES 发送邮件。
>
> 第三是 **站内信系统**，每次推送时自动生成站内信记录，APP 端可以查询消息列表、查看未读数、标记已读。
>
> 这个模块服务覆盖 14 种语言，支持按人群包定向推送，比如可以精准推给"注册 7 天内、未付费、使用 iOS 设备的日本用户"。

### 面试官追问："为什么用 XXL-Job 而不是直接定时器？"

> XXL-Job 是分布式任务调度平台，支持集群部署。我们有多台服务器，如果用 Spring 的 @Scheduled，每台服务器都会执行同一个任务，导致重复推送。XXL-Job 通过锁机制保证同一个任务在同一时刻只有一台服务器执行。而且它有可视化的管理界面，可以手动触发、查看执行日志，方便运维。

## 第三部分：数据库设计

### 面试官："说一下你的数据库设计"

**回答：**

> 推送模块核心有 6 张表：
>
> 1. **sys_push** — 推送配置主表，存储推送规则，包括触发类型、推送渠道、推送模式、触发时间等
> 2. **push_user** — 推送和用户的关联表，用于手动指定推送目标用户
> 3. **sys_push_crowd_pack_rel** — 推送和人群包的关联表，支持多个人群包
> 4. **crowd_pack** — 人群包定义表，存储筛选条件（付费状态、注册时间、国家、语言等）
> 5. **station_letter** — 站内信记录表，每次推送自动生成
> 6. **email_send_log** — 邮件发送流水表，记录每封邮件的发送状态

### 面试官追问："人群包是怎么设计的？"

> 人群包是一个独立的维度表，支持 10 多个筛选维度：付费类型（未付费/金币/VIP/通行证）、VIP 状态、注册时间（支持大于/小于/区间）、看广告次数、观看总时长、国家、语言、设备系统等。
>
> 关键设计是：**人群包被多个业务模块复用**，不只是推送，弹窗系统、活动系统、支付能力配置、广告策略都通过中间表关联人群包。这样运营只需要创建一次人群包，就可以在多个场景复用。
>
> 筛选逻辑是：一个推送规则关联多个人群包时，用户命中任意一个就算匹配（OR 逻辑）；单个人群包内部各维度之间是 AND 逻辑。

### 面试官追问："station_letter 的 message_id 是怎么设计的？"

> message_id 设计为 `push_{pushId}_{dateTag}_user_{userId}` 格式，比如 `push_123_20260727_user_456`。
>
> 这样设计的目的是**去重**：同一条推送规则在同一天对同一个用户只会生成一条站内信。插入前先查 message_id 是否存在，存在就跳过。
>
> 但有一个细节：**跨天可以重复**，因为 dateTag 不同。也就是说同一条规则明天再触发，会生成一条新的站内信。

## 第四部分：推送执行流程（核心）

### 面试官："详细说一下 App 推送的执行流程"

**按这个顺序讲：**

> 整个流程是 XXL-Job 每 5 分钟触发一次：
>
> **第一步：查询规则**
> 查询所有启用的推送规则，筛选 channel=0（App 推送）的规则
>
> **第二步：时间窗口筛选**
> 筛选出触发时间在 [now, now+5分钟] 窗口内的规则。这里有个细节：签到类型的推送只比较时分秒，不比较日期，所以每天同一时间都会触发；而新剧推送比较完整日期时间，只触发一次。
>
> **第三步：遍历每条规则执行推送**
> 根据 pushMode 分三种情况：
>
> - **pushMode=2（Topic 订阅）**：从字典表获取 FCM Topic 名称，调用 Firebase Topic 广播。这种方式不需要查用户设备表，FCM 服务端自动维护订阅列表。
>
> - **pushMode=0（指定人群）**：先查人群包筛选用户，再和 push_user 表手动指定的用户取并集。然后分批处理，每批 500 个用户。
>
> - **pushMode=1（不限人群）**：查所有最近 2 个月内活跃的用户，分批处理。
>
> **第四步：每批用户处理**
> 对于每个用户：
> 1. 生成站内信记录（去重检查）
> 2. 从 user_device 表获取 FCM Token
> 3. 构建推送消息（标题、内容、跳转参数、站内信 message_id）
> 4. 调用 Firebase 推送
>
> **第五步：Firebase 推送执行**
> Token 推送是分批的，每批最多 500 个 Token。如果有失败的 Token，会重试一次。返回成功和失败的 Token 列表。

### 面试官追问："签到时间跨天问题怎么解决的？"

> 线上版本的签到时间比较是简单的"今天/明天"判断，不支持跨天。比如当前时间 23:58，advance 5 分钟后是 00:03，签到时间 00:01 会被漏掉。
>
> 优化方案是**转成纯秒数比较**：把时分秒都转成当天的秒数（hour*3600 + minute*60 + second），然后判断签到秒数是否在 [当前秒数, 当前秒数+300秒] 区间内。如果跨越午夜（当前秒数 > advance 秒数），就判断签到秒数是否 >= 当前秒数 OR < advance 秒数。

### 面试官追问："为什么用 FCM Topic 而不是全量 Token 推送？"

> 两种模式配合使用，各有权衡：
>
> **Topic 广播**适合群发场景，比如"推送给所有英语用户"。优点是不需要查用户设备表，FCM 服务端自己维护订阅列表，性能好。缺点是不够精准，只能按语言分组。
>
> **Token 精准推送**适合定向场景，比如"推送给注册 7 天内未付费的日本用户"。优点是精准控制，缺点是需要逐个查 Token，用户量大时要分批处理。
>
> 我们的设计是：pushMode=0（指定人群）用 Token 精准推送，pushMode=2（Topic 订阅）用 Topic 广播。

### 面试官追问："推送失败怎么处理？"

> 分两层处理：
>
> **FCM 推送失败**：Firebase 的 sendEachForMulticast 方法会返回每个 Token 的发送结果。对于失败的 Token，我们会重试一次。如果还是失败，记录到日志里，但不会无限重试，因为可能是 Token 过期或者用户卸载了 App。
>
> **邮件发送失败**：邮件是通过 SQS 队列异步处理的。SES 发送失败后，结果会记录到 email_send_log 表，状态标记为 FAIL，并记录错误信息。SQS 本身有重试机制，消息消费失败会重新入队。

## 第五部分：邮件推送流程

### 面试官："邮件推送是怎么实现的？"

> 邮件推送的链路是：XXL-Job → SQS 队列 → Consumer → SES 发送
>
> 具体流程：
> 1. XXL-Job 的 emailPush Job 触发，筛选 channel=1（邮件）的规则
> 2. 获取目标用户，从 user_bind 表查询用户邮箱
> 3. 没有邮箱的用户记录 FAIL 到 email_send_log
> 4. 有邮箱的用户，构建 EmailSqsDTO，发送到 SQS 队列
> 5. EmailSqsConsumer 消费队列消息，调用 AWS SES 发送邮件
> 6. 发送结果记录到 email_send_log 表

### 面试官追问："为什么用 SQS 而不是直接调 SES？"

> 三个原因：
>
> **削峰**：定时任务可能一次产生数千封邮件，如果直接调 SES，瞬时压力太大。SQS 起到缓冲作用，Consumer 可以按自己的速度消费。
>
> **可靠性**：SQS 消息有可见性超时机制，Consumer 处理失败时消息会重新入队。而直接调 SES 如果网络抖动，邮件就丢了。
>
> **解耦**：推送调度和邮件发送解耦，互不影响。以后如果要换邮件服务商，只需要改 Consumer，不影响调度逻辑。

## 第六部分：站内信系统

### 面试官："站内信是怎么实现的？"

> 站内信是和推送绑定的，每次推送执行时自动生成站内信记录。
>
> **生成逻辑**：
> 1. 在推送的每批用户处理中，为每个目标用户生成一条 station_letter 记录
> 2. message_id 格式为 `push_{pushId}_{dateTag}_user_{userId}`
> 3. 插入前先查 message_id 是否存在，保证同规则同天同用户不重复
> 4. 存储推送标题、内容、图片、跳转信息、触发类型等
>
> **APP 端接口**：
> - 分页查询站内信列表，按发送时间倒序
> - 查询未读消息数（is_read=0 的记录数，超过 99 显示 99）
> - 标记单条消息已读（更新 is_read=1 和 read_time）
> - 一键全部已读
>
> **跳转逻辑**：
> 站内信有 jump_type 字段，0 表示跳转内部页面（如首页、剧集页），1 表示跳转 H5 链接（如活动页面）。APP 端根据这个字段决定跳转行为。

### 面试官追问："站内信的未读数是怎么统计的？"

> 直接查 station_letter 表，条件是 user_id=当前用户 AND is_read=0，用 COUNT 统计。如果超过 99，返回 99（前端显示要求）。
>
> 这个查询走了 user_id + is_read 的联合索引，性能没问题。

## 第七部分：语言隔离机制

### 面试官："多语言推送是怎么实现的？"

> 我们通过 FCM Topic 实现语言隔离，具体机制是：
>
> 1. **Topic 和语言一对一绑定**：每种语言对应一个 FCM Topic，比如中文是 `SarosTv_CN-31`，英语是 `SarosTv_US-31`，这些映射关系存在字典表里（dict_topic=SUBSCRIPTION_TOPIC）
>
> 2. **客户端订阅**：APP 根据用户的语言设置，调用 FCM SDK 订阅对应的 Topic
>
> 3. **推送时按 Topic 广播**：运营创建推送时选择语言，系统从字典表获取对应的 Topic 名称，调用 Firebase Topic 推送
>
> 4. **Token 推送时额外校验**：对于精准推送，除了查 Token，还会校验用户的 langId 是否和推送规则的 langId 一致，避免推错语言

### 面试官追问："如果用户切换语言怎么办？"

> 客户端会先取消订阅旧语言的 Topic，再订阅新语言的 Topic。这个操作是客户端 SDK 自动处理的，后端不需要额外逻辑。
>
> 但有一个细节：如果用户刚切换语言，Token 推送可能会有短暂的不一致，因为 user_device 表里的 langId 可能还没更新。不过这种情况很少见，而且用户手动切换语言后一般会重新打开 App，此时会重新上报 Token 和语言信息。

## 第八部分：技术选型追问

### 面试官："为什么选 Firebase 而不是自建推送？"

> 三个原因：
>
> **跨平台**：Firebase 支持 Android、iOS、Web，不用为每个平台单独对接推送服务（比如 iOS 的 APNs、Android 的 FCM）。Firebase 在底层帮我们处理了这些差异。
>
> **可靠性**：Firebase 是 Google 的服务，全球有节点，推送到达率高。自建推送服务要处理长连接、重试、去重等复杂问题，成本高。
>
> **开发效率**：Firebase 提供 Admin SDK，几行代码就能实现推送。自建的话要处理协议、序列化、错误处理等底层细节。

### 面试官："Redis 在这个模块里用在哪里？"

> 主要用在两个地方：
>
> **分布式锁**：Token 上报时用 Redisson 加分布式锁，防止同一设备并发上报导致数据不一致。锁的 key 是 deviceId，超时时间 5 秒。
>
> **FCM Token 缓存**：用户的 FCM Token 会缓存到 Redis，推送时先从 Redis 读，读不到再查数据库。但这个我做的版本主要是直接查 user_device 表，缓存是之前同事做的。

### 面试官："XXL-Job 的 5 分钟窗口是怎么理解的？"

> XXL-Job 每 5 分钟触发一次 push Job。每次触发时，查询触发时间在 [now, now+5分钟] 内的规则。
>
> 为什么要 5 分钟？因为推送不是实时要求很高的场景，5 分钟的延迟可以接受。而且这样可以批量处理，减少数据库查询次数。
>
> 有个细节：如果一条规则的触发时间是 12:03，而 Job 在 12:00 触发，这条规则会被筛选出来执行。如果 Job 在 12:05 再次触发，这条规则的触发时间已经不在 [12:05, 12:10] 窗口内了，所以不会重复推送。

## 第十部分：压力测试（面试官可能的刁钻问题）

### Q1："推送量有多大？"

> 具体数字我不太方便透露，但可以告诉你：我们平台覆盖 14 种语言，单次推送可能涉及几万到几十万用户。分批处理每批 500 个 Token，一批推送大概几秒钟完成。

### Q2："如果推送过程中服务器挂了怎么办？"

> XXL-Job 有失败重试机制，任务执行失败会根据配置的重试次数自动重试。而且我们的站内信有 message_id 去重，即使重试也不会重复生成站内信。
>
> FCM 推送本身是幂等的，同一个 Token 重复推送不会产生重复通知。

### Q3："用户量大的时候性能怎么保证？"

> 三个措施：
> 1. **分批处理**：每批 500 个 Token，避免单次请求过大
> 2. **异步处理**：邮件通过 SQS 异步，不阻塞主流程
> 3. **索引优化**：user_device 表的 user_id 有索引，station_letter 表的 user_id + is_read 有联合索引

### Q4："如何保证推送到达率？"

> 到达率主要靠 Firebase 保证，我们能做的是：
> 1. **Token 更新**：客户端每次打开 App 会重新上报 Token，保证 Token 有效
> 2. **失败重试**：推送失败的 Token 会重试一次
> 3. **语言校验**：推送前校验用户语言，避免推错语言导致用户关闭通知

### Q5："station_letter 表数据量大了怎么办？"

> 目前没有做分表，因为站内信是按用户隔离的，查询都是带 user_id 条件的，走了索引，性能还可以。
>
> 如果未来数据量增长，可以考虑：
> 1. 按用户 ID 哈希分表
> 2. 定期归档历史数据
> 3. 只保留最近 N 天的站内信

### Q6："人群包筛选性能怎么样？"

> 人群包筛选是 SQL 拼接条件查询 sys_user 表。因为条件都是 sys_user 表的字段（注册时间、VIP 状态、国家等），可以直接走索引。
>
> 如果关联多个人群包，是分别查询然后取并集，不是一次复杂查询。这样每次查询都比较简单，不会出现超时。

### Q7："推送内容是怎么存储的？"

> 推送内容存在 sys_push 表的 push_title 和 push_msg 字段，是运营在后台填写的。支持多语言，不同语言的推送创建不同的记录，通过 lang_id 区分。
>
> 站内信的内容是推送时冗余存储的，这样即使推送配置被修改或删除，站内信的内容也不会变。

### 四、签到时间比较的精确逻辑

```java
// 将时分秒转为当天秒数
int nowSeconds = hour * 3600 + minute * 60 + second;
int advanceSeconds = (hour+5分钟后的时分秒);
int signSeconds = signTime的时分秒;

if (nowSeconds <= advanceSeconds) {
    // 正常窗口（如 12:00 ~ 12:05）
    return signSeconds >= nowSeconds && signSeconds < advanceSeconds;
} else {
    // 跨天窗口（如 23:58 ~ 00:03）
    return signSeconds >= nowSeconds || signSeconds < advanceSeconds;
}
```

**关键点：**
- 只比较时分秒，不比较日期
- 使用秒数做数值比较，不是 Date 对象比较
- 跨天时用 OR 逻辑：在 [now, 24:00) 或 [00:00, advance) 内都算命中

### 六、FCM Token 上报的精确逻辑

```java
// 1. 加分布式锁（Redisson，5秒超时）
RLock lock = redissonClient.getLock(BasePrefix.PUSH_TOKEN_PREFIX + deviceId);
try {
    lock.lock(5, TimeUnit.SECONDS);

    // 2. 查 deviceId 是否已存在
    UserDeviceDAO existingDevice = userDeviceRepository.lambdaQuery()
        .eq(UserDeviceDAO::getDeviceId, deviceId)
        .one();

    if (existingDevice != null) {
        // 3. 已存在 → 更新 token 和 userId
        // 注意：会更新 userId，实现设备归属转移
        existingDevice.setToken(token);
        existingDevice.setUserId(userId);
        existingDevice.setUpdateTime(now);
        userDeviceRepository.updateById(existingDevice);
    } else {
        // 4. 不存在 → 新增
        UserDeviceDAO newDevice = new UserDeviceDAO();
        newDevice.setUserId(userId);
        newDevice.setDeviceId(deviceId);
        newDevice.setToken(token);
        newDevice.setDeviceSys(deviceSys);
        newDevice.setTimeCity(timeCity);
        userDeviceRepository.save(newDevice);
    }
} finally {
    lock.unlock();
}
```

**关键细节：**
- 一个 deviceId 只对应一条记录（upsert）
- 一个用户可以有多个设备
- 更新时会转移设备归属（userId 会更新）

### 十一、可能被问到的代码细节

**Q: 推送时为什么要 sleep 1 秒？**
> 每批推送之间 sleep 1 秒，是为了避免瞬时请求过大，给 Firebase 服务端造成压力。同时也避免触发 Firebase 的限流机制。

**Q: 站内信的 batchSentTime 是什么？**
> 每批用户处理时生成一个统一的时间戳 `LocalDateTime.now()`，这批用户的所有站内信都用这个时间。这样同一批次的站内信时间一致，不会因为循环处理导致时间差异。

**Q: 为什么邮件推送的活跃用户阈值是 2 个月，而 App 推送是 3 个月？**
> 这是业务配置，邮件推送更保守一些，只发给更活跃的用户，避免被标记为垃圾邮件。App 推送相对宽松，因为用户可以选择关闭通知。

**Q: getUserDeviceTokens 为什么要按 langId 过滤？**
> 如果推送规则指定了语言，需要过滤掉语言不匹配的用户。比如规则是推送给日语用户，但某个用户的 langId 是英语，即使他在目标用户列表里，也不应该收到推送。

**Q: 邮件推送的 SQS send 被注释了是什么情况？**
> 这是测试环境的状态，邮件发送功能还没有完全上线。正式环境会打开这个开关。Consumer 和 SES 的发送逻辑都已经实现了，只是 Producer 的 send 调用被注释了。
