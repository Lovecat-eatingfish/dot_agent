# 文件变更评审机制设计文档（事前 diff 审批 + 事后评审回滚）

> 对标：Claude Code 的「编辑前 diff 审批（accept / reject / accept-edits）」+ Codex auto 模式的「最终生成文件仍有接受/拒绝入口」。
> 分支：`dev_version6`。状态：**方案评审中，未开始编码**。

---

## 1. 背景与目标

当前 agent 在 EDIT / AUTO 模式下，`write_file` / `edit_file` 是**直接放行**的（`PermissionManager._check_inner` 中两个模式对文件写返回 ALLOW），用户既看不到"将要改什么"，也没有"改完之后反悔"的入口。只有 PLAN 模式的文件写、EDIT 模式的 bash 走了 ASK 人工审批，而审批弹窗（`PermissionModal`）只显示截断的原始参数字符串，没有 diff。

本设计补齐两条评审链路：

1. **事前审批（写之前拦）**：文件写操作在执行前展示 unified diff，用户选择 **接受 / 拒绝 / 本会话全部接受**，拒绝则该次工具调用不落盘。
2. **事后评审（写完之后仍可反悔）**：AUTO 模式下写入照常执行（不阻塞自动化），但每次变更登记进会话级 **变更台账（ChangeLedger）**；turn 结束给出变更汇总，用户可随时 `/review` 查看、`accept` / `revert`（回滚）任意一条或全部变更。

### 设计原则（沿用现有架构铁律）

- agent 层契约不动：`PermissionGate` 协议、`Decision` 三态、三级拦截顺序（系统黑名单 → 项目黑名单 → 模式规则）**均不改变**。评审能力全部落在 coding 层与 UI 层。
- 安全底线不突破：任何评审/接受机制都**不能放行**系统黑名单、项目黑名单（`.agent-security.json`）拦截的 DENY 操作。
- 无头不卡死：无交互环境（CI / 后台 / `agent run` 非交互）ASK 自动降级拒绝（现状保持），事后评审自动接受并留痕。
- 三环境一套内核：TUI（Textual 弹窗）/ Console（终端输入）/ 无头，仅交互层差异化。

## 3. 模式语义矩阵（唯一行为变更点，请重点审核）

| 模式 | read/glob/grep | write_file / edit_file | bash | 事后评审 |
|---|---|---|---|---|
| **PLAN** | ALLOW | **ASK（带 diff）**（现状即 ASK，补 diff） | DENY（现状） | 台账登记 |
| **EDIT** | ALLOW | **ASK（带 diff）** ← *行为变更：现状 ALLOW* | ASK（现状） | 台账登记 |
| **AUTO** | ALLOW | **ALLOW（照常自动落盘）** | ALLOW（现状） | **turn 结束汇总评审 + /review 随时可回滚** |

- **EDIT 的语义变更说明**：对标 Claude Code —— 交互编码模式下每次编辑先看 diff 再放行。担心打扰的用户在审批框按一次 `a`（本会话全部接受）即恢复"静默编辑"，效果等价于旧行为。这是把选择权交给用户而不是硬编码在模式里。
- **AUTO 不做事前拦截**：自动化场景不被打断，反悔能力由事后评审承担（这正是 Codex auto 模式的形态）。
- **会话级"全部接受"（session auto-accept）**：仅作用于模式规则层的写操作 ASK；系统/项目黑名单照常拦截；PLAN 模式不受它影响（PLAN 的写审批是模式语义本身，开关只豁免 EDIT）。会话结束或切换会话时重置。

## 4. 总体方案

### 4.1 事前审批链路（diff 提前到执行前）

```
工具调用 → extension before_hook → 权限三级拦截
                                        │ ASK（写操作）
                                        ▼
                    PermissionManager.ask_user()
                        │ ① ChangePreviewer.preview(tool, args)  ← 执行前模拟
                        │    write_file: 现有内容 vs 新 content 的 unified diff
                        │    edit_file:  应用 old_text→new_text 模拟替换后 diff
                        │ ② info 增加 preview 字段，交给 UI 审批
                        ▼
        ┌─ TUI: ChangeReviewModal（diff 渲染 + y/n/a）
        ├─ Console: 打印 diff + 输入 y/n/a
        └─ 无头: 自动拒绝（现状）
                            │
              y=True ┌──────┴──────┐ n=False
                     ▼              ▼
            重新 check(approved=True)   拒绝消息作为 tool result 返回给 agent
            放行执行工具                （"用户拒绝了本次修改"，agent 可调整方案）
```

要点：

- **预览在 `ask_user` 内计算**（coding 层内部），`loop.py`、`PermissionGate` 协议零改动。
- `edit_file` 预览同时提前暴露匹配错误：`old_text` 匹配 0 次或多次时，审批框直接显示"该替换无法唯一匹配"，用户可拒绝，省一次无效执行。
- 拒绝时返回给 agent 的 block_reason 从笼统的 mode 原因改为明确文案：`user rejected the change (reason)`，让 agent 知道是"人否了"而不是"权限不够"，可换方案重试。
- `a`（accept all）由 UI handler 回调 `PermissionManager.enable_session_auto_accept()` 后返回 True，**不扩展 `ask_user` 返回类型**（协议不变，coding 层内部消化）。

### 4.2 事后评审链路（ChangeLedger 变更台账）

```
写工具执行
  before_tool_call 链 → Ledger.before(call)     ← 记录执行前的文件内容快照（内存）
  工具执行（落盘）
  after_tool_call  链 → Ledger.after(call, result) ← 登记 FileChangeRecord（status=pending）

turn 结束 host.end_turn()
  → Ledger.checkpoint_turn(turn_id) → 返回变更摘要
  → TUI: 变更汇总面板（Enter=全部接受 / r=逐个评审 / Esc=保持 pending）
  → Console: 打印"N files changed, /review to inspect"
  → 无头: 自动全部接受（留痕）

随时（TUI / Console 通用）:
  /review            列出 pending 变更（路径、+/− 行数、状态、编号）
  /review show <id>  查看单条完整 diff
  /review accept <id|all>
  /review revert <id|all>   ← 回滚
```

#### 回滚（revert）实现——undo 栈 + git 兜底

每条 `FileChangeRecord` 持有该次写入**之前的文件内容快照**，同文件多次写入形成栈：

- `revert <id>`：用该记录的 before 快照恢复该文件（`Path.write_text`），记录状态置 `reverted`；对"本次新建"的文件（before 为空且执行前不存在）revert = 删除该文件。
- 同一文件连续 revert：沿栈逐级回退到更早的版本。
- 快照上限：单文件 512KB、会话累计 20MB；超限的记录标记 `fallback=git`，revert 改走 `SessionGit`：
  - 新增 `SessionGit.restore_paths(paths)`（实现：`git checkout HEAD -- <path>` / 新增文件用 `git rm` 或直接删除，利用 GIT_DIR + GIT_WORK_TREE 现成机制）。HEAD 即本 turn 开始前的状态，语义为"撤销该文件本 turn 的全部变更"。
- 已 accepted 的变更默认不回滚（用户明确 `/review revert all` 时例外：整个 turn 全量撤销）。

#### 状态机

```
FileChangeRecord.status:  pending ──accept──▶ accepted
                             │  ▲
                             └revert──▶ reverted（终态；同文件再次 revert 沿 undo 栈回退）
turn checkpoint 时未裁决的 pending → 自动 accepted（留痕 accepted-auto）
```

#### Agent 感知回滚（P1，默认开）

事后 revert 不回滚对话历史，agent 会误以为文件已改。P1 在 revert 发生时向 harness 注入一条提示消息（复用 `loop.py` 循环提示的 `ToolResultMessage` 形态）：`用户回滚了你对 <path> 的修改`。P0 先不做，在文档标注该认知偏差。

## 7. 数据结构（示意）

```python
# dot/coding/review/ledger.py
@dataclass
class FileChangeRecord:
    id: int                      # 会话内自增
    turn_id: int
    tool_call_id: str
    path: Path                   # workspace 相对路径
    kind: Literal["create", "update"]
    before: str | None           # 执行前内容（None = 新建且原不存在）
    before_bytes: int
    diff: str                    # 完整 unified diff（展示时再截断）
    fallback_git: bool           # 快照超限，回滚走 SessionGit
    status: Literal["pending", "accepted", "accepted-auto", "reverted"]
```

```python
# ask_user info 新增字段（dict 向后兼容，协议不变）
{
  "tool_name": "edit_file", "agent_mode": "edit",
  "source": "mode", "reason": "edit mode: file write needs approval",
  "args": {...},
  # ↓ 新增
  "preview": {
      "kind": "update",            # create | update | error
      "path": "src/.../ledger.py",
      "diff": "--- a/...\n+++ b/...",
      "truncated": False,
      "error": ""                  # edit 匹配 0/多次时的预检错误
  },
}
```

## 8. 安全与边界控制

1. **黑名单优先级不变**：评审/会话接受只作用于模式规则层 ASK；路径遍历、`denyFilePatterns`、`denyBashRegex` 命中即 DENY，任何确认不可放行（现有 `_check_inner` 顺序不动）。
2. **会话 auto-accept 生命周期**：`enable_session_auto_accept()` / `reset()`；切换会话（`resume_session`）时重置。
3. **快照内存上限**：单文件 512KB / 会话 20MB，超限走 git 兜底；SessionGit 不可用（`available=False`）时该记录标记 `not-revertible`，/review 展示时明示。
4. **并发**：工具调用在 loop 内顺序执行（`_run_tool_calls` for 循环），台账读写无并发问题；审批弹窗期间 loop 挂起等待（与现有 ASK 行为一致）。
5. **取消/中断**：审批中 Esc/中断 = 拒绝（现状语义）；agent 被 cancel 时已登记的 pending 记录保留，等用户裁决。
6. **审计留痕**：每条变更与裁决结果（含 auto-accept）追加进 trace span 与会话 JSONL（P0 写 trace，P1 持久化台账以便 resume 后恢复 pending 列表）。
