# 消息推送模块 — 面试详解版

> 用途：准备面试时的技术深度问答，覆盖架构、流程、表结构、技术决策、常见追问

---

## 一、模块概述

这个模块是为一个全球化的短剧流媒体 App（面向海外用户）构建的**多渠道消息推送系统**，包括：

| 子系统 | 说明 |
|--------|------|
| App 推送 | 基于 Firebase Cloud Messaging (FCM)，支持 Token 精准推送和 Topic 广播 |
| 邮件推送 | 基于 AWS SES + SQS 异步队列 |
| 站内信 | 推送时自动生成，APP 端可查询、标记已读 |
| 人群包系统 | 用户分群定向，被推送/弹窗/活动/支付等多个模块复用 |

**业务背景**：运营需要向全球不同语言、不同国家、不同付费状态的用户发送推送通知（新剧上线提醒、签到提醒、付费优惠、活动通知等），同时支持邮件营销触达。

## 三、数据库设计

### 3.1 核心表

```
sys_push (推送主表)
    ├── 1:N → push_user (手动指定的用户关联)
    ├── 1:N → sys_push_crowd_pack_rel (人群包关联)
    │            └── N:1 → crowd_pack (人群包定义)
    ├── 1:N → station_letter (自动生成的站内信)
    └── 1:N → email_send_log (邮件发送流水)

sys_user (用户表)
    ├── 1:N → user_device (设备表，含 FCM Token)
    └── 1:N → user_bind (三方绑定表，含邮箱)

sys_dict (字典表)
    └── dict_topic='SUBSCRIPTION_TOPIC' → FCM Topic 与语言的映射
```

### 3.2 推送主表 (sys_push) 关键字段

| 字段 | 说明 |
|------|------|
| trigger_type_code | 触发类型：sign(签到) / drama(新剧) / offers(优惠) / activity(活动) |
| channel | 推送渠道：0=App推送(FCM) / 1=邮件(SES) |
| push_mode | 推送模式：0=指定人群(人群包) / 1=不限人群 / 2=Topic订阅 |
| subscription_topic_id | FCM Topic 字典 ID |
| lang_id | 语言 ID，决定推给哪个语言群体 |
| states | 启用/禁用 |
| trigger_time | 触发时间（由 calculateTriggerTime 计算） |

### 3.3 人群包 (crowd_pack) 筛选维度

| 维度 | 说明 |
|------|------|
| 付费类型 | 未付费 / 金币 / VIP / 通行证（多选） |
| VIP 状态 | 是否 VIP |
| 注册时间 | ≥ / ≤ / 区间，单位：小时 |
| 看广告次数 | ≥ / ≤ / 区间 |
| 观看总时长 | ≥ / ≤ / 区间，单位：小时 |
| 国家 | 国家代码列表 |
| 语言 | 语言 ID 列表 |
| 设备系统 | iOS / Android |
| 渠道 | 来源渠道 |

### 3.4 站内信 (station_letter) 关键字段

| 字段 | 说明 |
|------|------|
| message_id | 全局唯一：`push_{pushId}_{dateTag}_user_{userId}` |
| is_read | 0=未读 / 1=已读 |
| jump_type | 0=内部页面 / 1=H5 链接 |

## 四、核心流程详解

### 4.1 推送配置（后台 CRUD）

**新增推送流程**：
1. 运营在后台填写：标题、内容、触发类型、推送渠道(App/邮件)、推送模式(人群包/不限/Topic)
2. 选择人群包（可多选）或手动指定用户
3. 系统自动：计算触发时间、补充短剧/剧集信息、校验语言一致性
4. 保存到 sys_push + push_user + sys_push_crowd_pack_rel

### 4.2 App 推送执行流程 (XXL-Job 触发)

```
XXL-Job "push" (每5分钟触发一次)
    │
    ▼
TimerServiceImpl.push()
    │
    ├── 1. 查询所有启用的推送规则 (channel=0)
    ├── 2. 筛选 [now, now+5min] 时间窗口内的规则
    │       ├── sign → 时分秒比较（支持跨天）
    │       ├── drama/offers/activity → 完整时间比较
    │
    └── 3. 遍历每条规则 → handleAppPush():
            │
            ├── pushMode=2 (Topic订阅):
            │   ├── 获取 FCM Topic 名称 (从字典表)
            │   ├── Firebase Topic 广播
            │   └── 遍历用户生成站内信
            │
            ├── pushMode=0 (指定人群):
            │   ├── 人群包条件筛选用户 + 手动指定用户 (取并集)
            │   ├── 分批 (500/批)
            │   │   ├── 生成站内信 (去重: 同规则+同天+同用户不重复)
            │   │   ├── 获取用户 FCM Token (从 user_device)
            │   │   └── Firebase Token 精准推送
            │
            └── pushMode=1 (不限人群):
                ├── 所有最近 N 个月内活跃的用户
                └── 同上分批处理
```

### 4.3 邮件推送执行流程

```
XXL-Job "emailPush" (每5分钟触发一次)
    │
    ├── 筛选 channel=1 的规则
    ├── 筛选时间窗口
    │
    └── 遍历规则 → handleEmailPush():
            ├── 获取目标用户 (同上)
            ├── 获取用户邮箱 (从 user_bind 表)
            ├── 无邮箱用户 → 记录 FAIL 到 email_send_log
            └── 有邮箱用户 → EmailService → SQS 队列
                    │
                    ▼
                EmailSqsConsumer 消费
                    │
                    ▼
                AWS SES 发送邮件
                    │
                    └── 记录结果到 email_send_log (SUCCESS/FAIL)
```

### 4.4 站内信 APP 端操作

**查询接口**：`GET /app/station/letter/page`
- 按 user_id 分页查询
- 按 is_read 排序（未读优先）

**未读数**：`GET /app/station/letter/unread/count`
- 统计 is_read=0 的记录数

**标记已读**：
- 单条：`POST /app/station/letter/{messageId}/read`
- 全部：`POST /app/station/letter/read/all`

### 4.5 语言隔离机制

```
用户的 langId (语言ID)
    │
    ▼
字典表 sys_dict (dict_topic='SUBSCRIPTION_TOPIC')
    ├── dict_value=1, dict_name='SarosTv_CN-31' → 中文用户订阅这个 Topic
    ├── dict_value=2, dict_name='SarosTv_US-31' → 英语用户
    ├── dict_value=4, dict_name='SarosTv_KR-31' → 韩语用户
    └── ...
```

- 客户端根据 langId 订阅对应 FCM Topic
- 推送时按 Topic 广播，自然实现语言隔离
- Token 精准推送时，额外校验用户的 langId 与推送规则的 langId 一致

## 五、技术要点（面试高频追问）

### Q1: 为什么用 FCM Topic 而不是全量 Token 推送？

**答**：两种模式配合使用：
- **Topic 广播**：适合"不限人群"或"按语言群发"的场景，不需要查用户设备表，FCM 服务端自动维护订阅列表，性能好
- **Token 精准推送**：适合"指定人群包"的场景，需要精确控制哪些用户收到，逐个查 Token 推送

### Q2: 站内信如何保证不重复？

**答**：messageId 设计为 `push_{pushId}_{dateTag}_user_{userId}`，同一条推送规则在同一天对同一个用户只会生成一条站内信。插入前先查 messageId 是否存在，存在则跳过。

### Q3: 推送的频控怎么做？

**答**：
- 定时任务扫描 `[now, now+5min]` 窗口，每个规则在窗口内只会被触发一次
- 站内信通过 messageId 去重（同规则+同天+同用户）
- 活动推送（另一套系统）有 `daily_trigger_limit` 字段控制每日上限

### Q4: 邮件推送为什么用 SQS 而不是直接调 SES？

**答**：
1. **削峰**：定时任务可能一次产生数千封邮件，SQS 起到缓冲作用
2. **可靠性**：SQS 消息有可见性超时和重试机制，SES 发送失败可以重试
3. **解耦**：推送调度和邮件发送解耦，互不影响

### Q5: 人群包是怎么筛选用户的？

**答**：人群包定义了多个维度条件（付费类型、VIP状态、注册时间、国家、语言等），筛选时用 SQL 拼接条件查询 sys_user 表，命中任何一个关联人群包的用户就被选中（OR 逻辑），人群包内部各维度之间是 AND 逻辑。

### Q6: 推送结果怎么追踪？

**答**：
- FCM 推送：`FireBaseServiceImpl` 返回成功/失败 Token 列表，失败的 Token 会重试一次
- 邮件推送：结果写入 `email_send_log` 表（SUCCESS/FAIL + 错误信息）
- 站内信：通过 `station_letter` 表的 `is_read` 追踪用户是否已读
- 推送事件上报：通过 `ConfigEventReportAdapter` 上报 PUSH_SHOW 事件

### Q7: 这个模块你具体做了哪些工作？

**答**（根据实际情况调整）：
1. **新增邮件推送渠道**：在原有 FCM 推送基础上，新增了邮件推送渠道（channel=1），对接 AWS SES + SQS
2. **人群包定向推送**：设计并实现了人群包系统，支持多维度用户分群（付费状态、注册时间、国家、语言等），被推送/弹窗/活动等多个模块复用
3. **站内信系统**：推送时自动生成站内信记录，实现 APP 端查询/未读统计/标记已读功能
4. **推送模式扩展**：支持三种推送模式（指定人群/不限人群/Topic订阅），满足不同运营场景
5. **签到时间跨天修复**：优化了签到推送的时间比较逻辑，解决了跨午夜窗口漏触发问题
6. **后台管理界面**：完善推送配置的 CRUD 接口，支持按人群包、剧名、语言等条件筛选
